## 2. Назначение и цели

### 2.1. Задача

Аналитик получает текст события: постановление, решение регулятора, санкции, новость. Нужно
быстро и проверяемо ответить, как событие отразится на портфеле: какие позиции затронуты,
какие потери возможны, где нарушатся ковенанты, что делать.

### 2.2. Цели системы

1. Построить по тексту события граф передачи шока «событие → канал → отрасль → фактор» и
   сценарий по факторам с помощью LLM, с цитатами из текста для каждой связи.
2. Дать аналитику подтвердить или исправить граф и сценарий до расчёта.
3. Посчитать каждую затронутую позицию моделью её типа на общей матрице сценариев и
   получить распределения метрик (P5/P50/P95) с происхождением каждого числа.
4. Собрать итоги по срезам портфеля сложением внутри общих реализаций.
5. Сформировать отчёт, в котором каждое число ссылается на метрику, и передать его на
   утверждение риск-менеджеру.
6. Отвечать на вопросы по рассчитанному прогону числами, прочитанными из прогона.
7. Подключать новые типы инструментов, модели, факторы, срезы, агентов, инструменты агентов
   и экраны плагинами без правки ядра.

### 2.3. Границы применения

Результаты — расчёт для сценарного анализа, раннего предупреждения и ранжирования
позиций для ручной проверки. Система **не предназначена** для автоматических кредитных
решений, регуляторных PD/LGD/EAD, резервов по МСФО 9, бухгалтерской и регуляторной
отчётности, справедливой стоимости и торговых решений. Эти ограничения записываются в
каждый результат (`limits`).

### 2.4. Принципы

- **Никаких молчаливых умолчаний.** Отсутствующий вход либо обязателен, либо имеет
  объявленное умолчание, флаг допущения которого доходит до результата.
- **Каждое число с источником.** Число входа — `Parameter(value, unit, evidence)`; число
  отчёта — ссылка на путь в дереве метрик.
- **Человек в контуре.** Расчёт не начинается без подтверждённого сценария, отчёт не
  публикуется без решения риск-менеджера.
- **Квантили вместе.** P5, P50 и P95 показываются только вместе.
- **Воспроизводимость.** Прогон фиксирует код, данные, сценарий и зерно; повтор даёт те
  же числа.

## 3. Пользователи и роли

| Роль | Кто | Что может |
|---|---|---|
| `analyst` | аналитик | создаёт прогоны, подтверждает и правит граф и сценарий, задаёт вопросы по результатам, редактирует демо-портфели |
| `risk_manager` | риск-менеджер | утверждает, возвращает с причиной или отклоняет отчёт; задаёт вопросы по результатам |
| `admin` | администратор | всё перечисленное; загрузка рабочих портфелей и снимков данных |
| `demo` | демонстрационный ключ | только демо-контур; объединяет права аналитика и риск-менеджера |

Кроме ролей, ключ несёт области доступа (`production:*`, `demo:*`). Ключ роли `demo` не
получает доступа к рабочему контуру.

## 4. Архитектура

### 4.1. Ядро и плагины

Ядро не знает типов инструментов и конкретных агентов. Оно даёт общие возможности:
данные на дату оценки, общий сценарий, диспетчер моделей, агрегацию по срезам, отчёт с
проверяемыми числами, процессы LangGraph с остановками для человека, MCP и аудит. Всё
предметное подключается плагинами.

| Слой | Каталог | Ответственность |
|---|---|---|
| Контракты | `src/msa/contracts/` | pydantic-модели обмена: домен, снимок, граф, сценарий, результат, отчёт, объяснение |
| SDK плагинов | `src/msa/plugin_sdk/` | всё, что объявляет и использует плагин (раздел 10) |
| Реестр | `src/msa/platform/` | загрузка встроенного объявления `core` и плагинов, проверка объявлений, каталоги |
| Движок | `src/msa/engine/` | снимок и разрешение данных, сценарии, передача шока, диспетчер, срезы, Шепли |
| Агенты | `src/msa/agents/` | агенты процесса ядра и агент объяснения |
| Граф выполнения | `src/msa/graph/` | компилятор процессов, узлы, журнал, остановки, чекпоинты |
| Процессы | `src/msa/workflows/` | встроенное объявление `core`: `stress_test`, `explain_results`, MCP ядра |
| MCP | `src/msa/mcp/` | серверы из реестра, шлюз, аудит вызовов |
| Отчёт | `src/msa/reporting/` | дерево метрик, отчёт, рекомендации, трасса |
| Валидаторы | `src/msa/validators/` | V1–V3, V7–V9, V11 |
| API | `src/msa/api/` | HTTP, очередь прогонов, раздача интерфейса |
| БД | `src/msa/db/`, `migrations/` | таблицы, репозитории, миграция `p0001` |
| Интеграции | `src/msa/integrations/` | клиенты LLM, разбор PDF/DOCX (docling) |
| CLI | `src/msa/cli/` | `msa-plugin` и шаблоны плагинов |
| Плагины | `src/msa/plugins/<id>/` | типы инструментов, модели, факторы, срезы, агенты, MCP-серверы плагинов |
| Интерфейс | `ui/web/` | браузерное приложение и UI-плагины |

### 4.2. Правила зависимостей

Проверяются автоматически (`uv run --frozen lint-imports`, контракты в `pyproject.toml`, и
`tests/platform/test_core_boundary.py`):

1. Ядро не импортирует `msa.plugins`.
2. Плагин импортирует только `msa.plugin_sdk`, `msa.contracts` и собственный пакет; тестам
   плагина разрешено ядро.
3. Плагины не импортируют друг друга; исключение — базовый плагин `market`.
4. Ядро не называет плагины: идентификаторы плагинов, типов инструментов, видов снимка и
   префиксы `<id>.` не встречаются строковыми литералами в коде ядра (Python без
   docstring, TS/TSX вне `ui/web/src/plugins/<id>/`).

### 4.3. Контуры

| Контур | Путь API | Данные | LLM | Калибровка PD |
|---|---|---|---|---|
| демо | `/v1/demo/...`, схема БД `demo` | синтетические портфели, снимки и события на 11.09.2026 | любая, включая DeepSeek | синтетический реестр `demo-synthetic-2026-09`, каждый результат помечен |
| рабочий | `/v1/...` | портфели и снимки банка | только в контуре банка (`local`) или без модели | файл банка из `MSA_CALIBRATION_REGISTRY`; без него — балл риска без денежных потерь |

Внешняя LLM в рабочий контур не допускается ни для прогонов, ни для объяснений (ответ 409).

### 4.4. Профили LLM

`MSA_LLM_PROVIDER`: `local` (OpenAI-совместимый сервер, `MSA_LLM_BASE_URL`,
`MSA_LLM_MODEL`), `deepseek` (ключ из переменной окружения пользователя
`DEEPSEEK_API_KEY`), `mock` (без модели: граф строится по отраслям портфеля или берётся
готовый ответ события). Вызов инструментов включён для `local` и `deepseek`,
`MSA_LLM_TOOL_CALLING` переопределяет. Запрос прогона с `strong_model: true` использует
более сильную модель профиля (`deepseek-v4-pro`), модель записывается в версии прогона.
Ответы LLM принимаются только в структурированном виде (JSON Schema или `json_object`) и
проверяются контрактами.

## 5. Модель данных

### 5.1. Домен

```
Party (эмитент, контрагент: ОКВЭД, страна)
  └─ Instrument (instrument_type, currency, terms по схеме типа, schema_version, issuer_id)
       └─ Position (params по схеме типа, model_id — явный выбор модели или умолчание типа)
Portfolio (base_currency, as_of, snapshot_id)   ── PortfolioBundle: всё вместе, ссылки проверены
DataSnapshot (as_of, items: SnapshotItem)        ── данные на дату оценки
```

Требования:

- `terms` и `params` проверяются по версионированным схемам типа из реестра. Неизвестный
  тип, чужая версия схемы и лишнее поле отклоняются с объяснением (валидатор V2).
- Единицы только из `contracts/units.py`: простые (`fraction`, `days`, `ratio`,
  `shares`, `log_return`, …), деньги `<CCY>_million`, цены `<CCY>_per_unit`. В
  объявлениях допустимо `base_money` — миллионы базовой валюты портфеля.
- `Evidence` — документ, историческая оценка или допущение эксперта с автором и датой.

### 5.2. Снимок данных

`SnapshotItem(item_id, kind, subject, observed_on, values, attributes, evidence)`: цена,
курс, отчётность, чувствительности, дивиденды, кривая ставок.

- Снимок неизменяем: повторная загрузка того же содержимого ничего не меняет, другое
  содержимое под тем же id отклоняется (409). Элемент позже `as_of` снимка отклоняется.
- Модель объявляет требования (`DataRequirement`). Платформа выбирает последний элемент
  **не позже даты оценки прогона** и записывает причину всего, что не нашлось: `missing`
  или `dated_after_as_of`.
- Аналоги (`peers_of`) подбираются по глубине совпадения ОКВЭД.

### 5.3. Граф события

`TransmissionGraph`: узлы `event`, `channel`, `sector` (с ОКВЭД), `factor` (с
идентификатором фактора и, для прямого фактора, ключом). Ребро: знак ±1, эластичность
(точка, треугольное, равномерное или логнормальное распределение), лаг 0–36 месяцев, не
меньше одного источника. Граф ациклический, рёбра уникальны.

### 5.4. Сценарий

`MacroParameter` двигает один фактор: распределение (`point`, `triangular`, `uniform`,
`truncated_normal`), единица, фактор, ключ (для прямого фактора) или канал (для фактора
через граф). Параметр без фактора описывает структурный вход модели и раскрывается как
неиспользованный моделями, которые его не читают.

### 5.5. Результат позиции

`CalculationResult` — общий конверт любой модели:

| Поле | Смысл |
|---|---|
| `position_id`, `instrument_type`, `plugin_id/version`, `model_id/version` | что и чем посчитано |
| `as_of`, `horizon`, `seed`, `base_currency`, `scenario_id`, `snapshot_id`, `macro_draws_sha256` | на чём |
| `execution` | `completed`, `not_run`, `failed` |
| `status`, `applicability`, `data_quality` | насколько можно доверять: `ok`, `needs_review`, `uncalibrated`, `incomplete`, `invalid` |
| `metrics` | значение и/или P5/P50/P95 (+ES95) в объявленной единице |
| `details`, `details_schema` | собственный результат модели |
| `input_sources`, `sources`, `assumptions`, `flags`, `diagnostics`, `limits` | происхождение и ограничения |
| `contributions` | вклады в срезы: мера, единица, горизонт, размер, допуск, реализации |

## 6. Процесс стресс-теста

Процесс `stress_test` объявлен данными (`WorkflowSpec`, `src/msa/workflows/stress_test.py`)
и собирается компилятором в граф LangGraph. Точки расширения — в квадратных скобках.

```
ingest ─► [after_event_parsed] ─► causal_agent ─► validate_causal ─┬─► causal_agent (повтор)
                                                                    └─► [before_scenario_approval]
 ─► human_fix_graph (остановка) ─► exposure_profiler ─► draw_macro ─► quant_agent × N
 ─► aggregate ─► [after_calculation] ─► advisory_agent ─► [before_report]
 ─► human_approval (остановка) ─► publish
```

### 6.1. Приём события (`ingest`)

- Источники: текст, URL (только `https` и хосты из `MSA_INGEST_URL_HOSTS`), загруженный
  документ PDF/DOCX (`POST /documents`, разбор docling при загрузке), событие демо-библиотеки.
- Текст режется на адресуемые фрагменты с SHA-256: предложения текста и слов аналитика о
  силе события, абзацы и ячейки таблиц документа. Связи графа цитируют эти фрагменты.
- Аналитик может описать силу события своими словами (до 4000 символов).

### 6.2. Причинный агент (`causal_agent`)

- Получает фрагменты события и контекст моделей портфеля из реестра: типы инструментов,
  описания моделей, ОКВЭД эмитентов, горизонт, требования моделей и полные объявления
  факторов. Денежные суммы позиций и данные снимка агенту не передаются.
- Возвращает граф влияния, паспорт события и сценарий: параметры по факторам моделей
  текущего портфеля (факторы моделей, которых в портфеле нет, агенту не доступны).
- Если событие указывает влияние на фактор, но не задаёт величину, модель оценивает её
  диапазоном (треугольное распределение). Сервер записывает такой параметр как допущение с
  автором `LLM:<модель> (оценка модели)` и датой.
- Промпт версионирован (`prompts/templates/causal-v<N>.txt`), версия записывается в
  прогон.

### 6.3. Проверка графа и сценария (`validate_causal`)

| Правило | Что проверяет |
|---|---|
| V1 | ответ соответствует контракту |
| V2 | узлы факторов называют зарегистрированные факторы, прямые факторы — ключ; единицы и схемы |
| V3 | каждая цепочка, начатая событием, доходит до узла фактора |
| V7 | граф ациклический |
| V8 | у каждого ребра есть источник |
| SCENARIO | каждый затронутый фактор достигнутой позиции получил параметр сценария |

Ошибки возвращаются LLM на исправление. Всего не больше трёх попыток; после исчерпания
попыток или при ревизии аналитиком процесс идёт к остановке для человека. Проверяются все
затронутые факторы, даже если один уже задан. Явный нулевой сценарий допустим;
отсутствие параметра не означает нулевой риск.

### 6.4. Подтверждение аналитиком (`human_fix_graph`)

Остановка обязательна, если сценарий требует подтверждения, запрошен просмотр графа
(`request_graph_review`) или проверки не прошли. Аналитик правит узлы, рёбра,
эластичности, лаги и параметры, видит предпросмотр шока по позициям и проверку черновика
(`POST /scenario-check`). Изменённая аналитиком величина становится его допущением;
параметр, добавленный аналитиком, записывается с источником «сценарий, заданный
аналитиком». Каждое подтверждение увеличивает ревизию графа.

### 6.5. Экспозиция (`exposure_profiler`)

Для каждой позиции определяется, достигает ли её сценарий: через граф (отрасль графа
покрывает ОКВЭД эмитента, см. [math.md, 3.5](math.md#35-сопоставление-отрасли-по-оквэд)) или
через прямой фактор по ключу. Позиции, которых событие не достигло, не считаются, но
измеряются для покрытия и концентрации. Данные на дату оценки читаются через
`mcp-portfolio.resolve_inputs`.

### 6.6. Сценарная матрица (`draw_macro`)

Один раз на прогон: 8 реплик Соболя, всего 8192, 16384 или 32768 реализаций (по умолчанию
8192, то есть 1024 точки в реплике), зерно по умолчанию 20260911. Собственные шоки позиций и
неопределённые эластичности рёбер — из отдельных детерминированных потоков. Формулы — в
[math.md, раздел 2](math.md#2-сценарий-и-совместные-реализации). `scenario_id` — хеш
спецификации сценария, зерна, даты оценки, горизонта, графа, версий факторов и хеша
матрицы.

### 6.7. Расчёт позиций (`quant_agent × N`)

Узел выполняется параллельно для каждой позиции (`Send`) и вызывает
`mcp-models.run_model`. Шаги диспетчера (`engine/dispatch.py`):

1. проверка `terms`, `params`, `schema_version`;
2. `model.requirements()` и разрешение данных по снимку;
3. `model.validate(prepared)`: ошибки, размеры позиции по срезам, собственные шоки. Ошибка
   даёт `execution="not_run"` с причиной и размером для покрытия;
4. `model.calculate(prepared, context)`: платформа пересоздаёт реализации и сверяет
   `scenario_id`;
5. проверка выхода (`output_problems`): идентичность, объявленные метрики и единицы,
   обязательные метрики, форма распределений, срез, единица и длина реализаций вклада, схема
   `details`.

Исключение модели становится результатом `failed` с флагом `model_error:<Тип>` и не
останавливает остальные позиции. Горизонт расчёта — 12 месяцев.

### 6.8. Агрегация (`aggregate`)

Срезы портфеля собираются из вкладов позиций (раздел 8.1). Валидатор V11 проверяет, что
все ветки использовали одну матрицу сценариев. Результаты позиций и срезов записываются в
прогон сразу после этого шага: числа доступны, пока пишется отчёт.

### 6.9. Отчёт (`advisory_agent`)

Отчёт собирается из общих разделов и разделов плагинов, рекомендации — по правилам
плагинов (раздел 8.3); каждое число шаблонного текста — ссылка на дерево метрик. LLM может
переписать итоговый текст; валидатор V9 принимает его, только если каждое число
прослеживается к тому же дереву, иначе остаётся шаблонный текст. Промпт версионирован
(`advisory-v<N>.txt`).

### 6.10. Решение риск-менеджера (`human_approval`) и публикация

Риск-менеджер утверждает, возвращает с причиной или отклоняет отчёт. Возврат ведёт к
новой ревизии. Ни одна точка расширения не лежит на пути в обход этой остановки и
подтверждения сценария. В демо-контуре для репетиций допускается `auto_approve`.

### 6.11. Статусы прогона

Прогон виден через `GET /runs/{id}`: текущий и следующие узлы, ожидание ответа LLM
(`llm_waiting`), остановка для человека, ошибка с причиной. После каждого шага
`RunService` записывает завершённый узел.

## 7. Расчётные модели

Модели — часть плагинов. Все формулы — в [math.md](math.md). Требования ниже задают
поведение, которое должно сохраняться при изменениях.

### 7.1. Кредит (`credit` 3.3.0)

| Что | Значение |
|---|---|
| Типы | `corp_loan`, `bond_fixed`, `bond_floater`, `pf_escrow`, `leasing` |
| Модели | `credit.corporate.v3`, `credit.bond.v3`, `credit.project_finance.v3`, `credit.leasing.v3` |
| Факторы (через граф) | `credit.revenue`, `credit.cogs`, `credit.logistics`, `credit.working_capital` (дни), `credit.interest` (годовые пункты), `credit.capex`, `credit.fx` |
| Срез | `credit.loss` — рост ожидаемых потерь, база EAD |
| Виды снимка | `financial_statement`, `rate` |

Требования к модели:

- помесячная модель заёмщика на горизонте: операционная компания (выручка, затраты,
  оборотный капитал, налог, capex, долг по траншам, возобновляемая линия, денежный поток,
  ликвидность), проектное финансирование с эскроу, лизинговая компания;
- PD по логистической модели сегмента; без утверждённой калибровки — балл риска со
  статусом `uncalibrated` без денежных потерь;
- ожидаемые потери и их рост (ΔEL) — вклад в срез `credit.loss`;
- ковенанты (ICR, чистый долг/EBITDA, покрытие эскроу, долг/капитал) с вероятностью
  нарушения по траекториям, запасом и месяцем нарушения;
- ликвидность: минимальный запас, дефицит финансирования, превышение лимита;
- облигации: переоценка по условиям выпуска или утверждённой рыночной калибровке;
- вклад каналов по Шепли, обратный стресс-тест по каждому ковенанту;
- пять осей риска; без утверждённых правил оси — «не оценено»;
- качество данных и подстановка аналогов при низком качестве;
- правила R1–R5 и действия `restructure`, `add_collateral`, `covenant_talks`,
  `limit_cut`, `hedge`, `watchlist`;
- правило включения результатов `needs_review` в срез с раскрытием (из реестра
  калибровок).

Эталон: `src/msa/plugins/credit/tests/test_credit_reference.py` сверяет все позиции
`MULTI-ASSET` и `ATYPICAL-BORROWERS` и срез с `credit_reference.json` (относительный допуск
1e-8). Эталон переписывается только при задуманном изменении чисел, с объяснением в
сообщении коммита.

### 7.2. Акции (`equity` 1.1.0)

| Что | Значение |
|---|---|
| Тип | `common_stock` (длинные позиции) |
| Модель | `equity.factor_stress.v1` |
| Факторы | `equity.market` (прямой, ключ — индекс), `equity.sector` (через граф по ОКВЭД), `market.fx` |
| Срез | вклад в `market.pnl` |
| Виды снимка | `sensitivity` (беты, остаточная волатильность), `dividend` |

Требования: цена на горизонте по факторам и остаточному шоку, валютная переоценка,
дивиденды за горизонт; метрики стоимости, результата, потерь, дивидендов, логарифмической
доходности; вклад факторов по Шепли; гистограмма потерь. Отсутствие цены, курса,
чувствительности или объявления дивидендов останавливает позицию; нулевой остаточный риск
и нулевые дивиденды задаются явно. Правила E1, E2.

### 7.3. Рынок (`market` 1.0.0)

Базовый плагин рыночных семейств: фактор `market.fx`, срез `market.pnl`, виды снимка
`fx_rate` и `price`, помощники `fx.requirement`, `fx.factor`, `fx.spot`, `fx.log_change`.
Отсутствующий курс — ошибка позиции, никогда не молчаливая единица.

### 7.4. Исследовательские агенты (`research` 1.1.0)

Пример агентного плагина, выключен по умолчанию: `research.concentration` (подграф с циклом
по срезам), `research.brief` (читает вывод предыдущего агента), `research.digest` (вызывает
собственный MCP-инструмент `research.notes.slice_digest`).

## 8. Агрегация, отчёт и происхождение чисел

### 8.1. Срезы портфеля

- Срез — одна мера с одним смыслом (`SliceSpec`). Потери допущенных позиций складываются
  внутри каждой реализации, затем считаются P5/P50/P95, VaR95, ES95, вклады позиций в ES95
  ([math.md, раздел 6](math.md#6-агрегация-по-срезам-портфеля)).
- Срезы между собой не складываются.
- Допуск вклада: `included`; `admitted:<правило>` для `needs_review` по утверждённому
  правилу; `excluded:<причина>`; `incompatible:<причина>` при другой единице, горизонте или
  `scenario_id`.
- Покрытие — по базе среза среди всех позиций среза, рассчитанных и нет. Срез `incomplete`,
  если непокрытая доля выше `coverage_limit` (0,05) или размер позиции нельзя измерить.
- Концентрация (индекс Херфиндаля) — по всему портфелю на базе среза; доля портфеля,
  затронутая событием, показывается отдельно.
- Позиции вне всех срезов перечисляются в `not_aggregated` с причиной.

### 8.2. Дерево метрик

Единый адресуемый вид чисел прогона (`reporting/tree.py`):
`/positions/<id>/metrics/<metric>/p50`, проекции плагинов
(`/positions/<id>/covenants/…`), `/portfolio/slices/<id>/loss_quantiles/p95`. Его читают
отчёт, V9, экраны, трасса и MCP.

### 8.3. Отчёт и рекомендации

- Разделы: итог по срезам, рекомендации, ограничения, допущения и авторы, разделы
  плагинов. Разделы пишут числа только через `ReportContext.cite(path)` или
  `ReportContext.interval(path, unit)`.
- Рекомендации — таблица правил плагинов над наблюдениями. Пороги в силе хранятся в журнале
  `rule_threshold`; без утверждённого значения действует порог объявления, и отчёт это
  раскрывает.
- Отчёт с числом без ссылки не проходит V9.

### 8.4. Трасса

`GET /runs/{id}/trace` показывает для каждого числа отчёта значение, узлы и источники:
данные позиции, фрагменты события на пути к её отрасли и параметры сценария, дошедшие до
неё.

## 9. Объяснение результатов

- `POST /runs/{id}/explanations {"question": …}` — вопрос о рассчитанном прогоне (без
  результатов — 409; в рабочем контуре с внешней LLM — 409). Ответ готовит процесс
  `explain_results` в фоне.
- Агент — ограниченный цикл LLM ↔ инструменты `mcp-runs` (`get_run_summary`,
  `get_position_metrics`, `get_metric_provenance`, `describe_model`): не больше 6 шагов
  модели и 12 вызовов. Инструменты только читают и привязаны к прогону вызова; модель не
  видит `run_id`.
- Каждое число ответа ищется в ответах инструментов
  ([math.md, раздел 7](math.md#7-проверка-чисел-в-тексте)). Непроверенные числа получают
  одну попытку исправления. Иначе, а также без вызова инструментов или при исчерпании
  лимитов, ответ собирается из сводки прогона без модели (`mode="structured"`), причина
  раскрывается.
- Вызовы записываются в аудит под узлом `explain/<id>` с инициатором `llm`.

## 10. Расширяемость плагинами

Цель архитектуры — фиксированное ядро, к которому всё предметное подключается плагинами.
Критерий: **новый плагин создаётся без единой правки вне двух его папок.** Если плагину
нужна правка ядра, это недостающая точка расширения SDK; её добавляют отдельным изменением
ядра с ростом минорной версии SDK, а не частным случаем в ядре. Полное руководство — в
[docs/plugins.md](../plugins.md).

### 10.1. Что расширяется

| Расширение | Объявление в `Plugin` | Где появляется без правки ядра |
|---|---|---|
| Тип инструмента | `instrument_types` (`InstrumentTypeSpec`) | каталог, проверка портфеля, редактор портфеля, MCP |
| Расчётная модель | `models` (`CalculationModel`) | диспетчер, `mcp-models.run_model`, `/v1/models`, выбор модели в запросе прогона |
| Метрика | `metrics` (`MetricSpec`) | результат, дерево метрик, отчёт, экраны, объяснение |
| Фактор сценария | `factors` (`FactorSpec`) | сценарий, граф события, промпт причинного агента, `/v1/factors` |
| Срез портфеля | `slices` (`SliceSpec`) | агрегатор, вкладка «Портфель», отчёт |
| Вид данных снимка | `snapshot_kinds` (`SnapshotKindSpec`) | импорт снимка, каталог |
| Экран результата | `views` (`ResultView`) и UI-плагин | карточка позиции |
| Разделы отчёта | `report_sections`, `tree` | текст отчёта с проверяемыми числами |
| Правила рекомендаций | `observations`, `rules`, `actions` | рекомендации, журнал порогов |
| Слова флагов, источников, авторов | `flags`, `informational_flags`, `sources`, `authors` | отчёт, экраны, MCP |
| Параметры контура | `run_options`, `notes` | модели получают их в `RunOptions.options`; отчёт раскрывает `notes` |
| Агент | `agents` (`AgentPlugin`) | точка расширения процесса, журнал, аудит, экран вызовов |
| MCP-сервер | `mcp_servers` (`McpServerSpec`) | шлюз MCP с аудитом |
| Промпт | `prompts` и файл `prompts/<name>-v<N>.txt` | `plugin_sdk.prompts.prompt("<id>.<name>")` |
| Процесс | `workflows` (`WorkflowSpec`) | компилятор, `/v1/workflows`, шкала этапов |
| Демо-данные | папка `demo_data/` | демо-портфели и демо-снимок |

Идентификаторы метрик, факторов, срезов, моделей, правил, видов, разделов, агентов,
MCP-серверов и промптов начинаются с `<plugin_id>.`. Глобальны только идентификаторы типа
инструмента, вида снимка, действия и процесса; их уникальность проверяет реестр.

### 10.2. Раскладка плагина

```
src/msa/plugins/<id>/
  __init__.py        plugin = Plugin(...)
  *.py               модели, схемы, отчёт, агенты, MCP-серверы
  prompts/           промпты агентов: <name>-v<N>.txt
  demo_data/         части демо-портфелей и демо-снимка
  tests/             тесты плагина (пакет)
  README.md          что даёт плагин, ограничения, открытые вопросы
ui/web/src/plugins/<id>/        (по желанию)
  plugin.json        версии сервера, компоненты видов, агенты
  index.tsx          UiPlugin: views, agents, notes, glosses, glossary, baseline
```

Реестр находит плагины в `msa.plugins` при старте и проверяет объявление целиком. Ошибка
объявления или несовместимая версия SDK блокирует старт с названием плагина.

### 10.3. Контракт расчётной модели

Модель — наследник `CalculationModel` с тремя шагами. Модель **чистая**: не обращается к
БД, сети и LLM и видит только подготовленные входы и сценарий.

| Шаг | Вход | Выход | Требования |
|---|---|---|---|
| `requirements(position, options)` | позиция с инструментом и эмитентом | `DataRequirements`: элементы снимка и `FactorRequirement` | данные ещё не прочитаны; валютный инструмент запрашивает курс и фактор `market.fx` |
| `validate(prepared)` | подготовленные входы | `Diagnostics`: ошибки, размеры по срезам, собственные шоки, качество данных | размер позиции возвращается и когда она не считается |
| `calculate(prepared, context)` | входы и `context.scenario` | `CalculationResult` через `envelope()` | сценарий читается только через `ScenarioView`: `parameters_for`, `draws`, `central`, `idiosyncratic`; вклад в срез — потери в каждой реализации |

Общие вычисления модель берёт из `msa.plugin_sdk.calc` (реализации сценария, сигнал фактора
через граф, проверка области, ES, Шепли, качество данных, хеш кода), помощники отчёта — из
`msa.plugin_sdk.report`. Модули `msa.engine` и `msa.reporting` плагин не импортирует.

### 10.4. Факторы и срезы

| `scope` фактора | Как доходит до позиции | Пример |
|---|---|---|
| `graph` | через канал графа события и отрасль (ОКВЭД) к узлу фактора, с эластичностями и лагами | `credit.revenue`, `equity.sector` |
| `global` | напрямую по ключу, одинаково для всех | `equity.market`, ключ `MOEX` |
| `sector` | напрямую по отраслевому ключу | отраслевой фактор |
| `instrument` | напрямую по идентификатору инструмента | собственный фактор бумаги |
| `currency_pair` | напрямую по паре `CCY/BASE` | `market.fx`, ключ `USD/RUB` |

`application` (`relative`, `additive`, `log`), `quantity` и `unit` описывают, как шок меняет
величину. Графовые факторы автоматически попадают в промпт причинного агента, редактор
графа и проверку сценария. Новый плагин может вносить вклад в существующий срез или
объявить свой; вклад принимается, только если совпадают единица, горизонт и `scenario_id`.

### 10.5. Агенты и точки расширения

Процесс — данные: узлы, рёбра, маршруты, этапы и точки расширения. Компилятор вставляет
агентов плагинов после их точки.

| Процесс | Точки расширения |
|---|---|
| `stress_test` | `after_event_parsed`, `before_scenario_approval`, `after_calculation`, `before_report` |
| `explain_results` | `after_explanation` |

Требования к агенту (`AgentPlugin`):

- **Чтение** — только `consumes` из набора, гарантированного точкой (`available`), и
  идентичность прогона; вывод другого агента — ключом `ext:<agent_id>/<key>` при порядке
  `after`.
- **Запись** — только объявленные `produces` в собственное пространство
  `extensions[<agent_id>]`; запись ключа ядра отклоняется при компиляции, необъявленного
  ключа — при выполнении. Вывод проверяется `output_schema`.
- **Порядок** — слои по `before`/`after`; агенты одного слоя работают параллельно.
- **Ограничения** — `timeout_s`, `retries` (1–3), `max_iterations` для подграфа с циклом.
- **Сбой** агента-плагина записывается в его пространство (`{"failed": true, "errors":
  [...]}`) и не останавливает прогон.
- **Инструменты** — только объявленные в `tools` (`"<server>.<tool>"`), вызов через
  `AgentContext.tools` с аудитом; LLM — `AgentContext.llm` (`None` без модели).
- **Включение** — в запросе прогона (`agents`), переменной `MSA_AGENT_PLUGINS` или
  `enabled_by_default=True` (только для агентов, без которых процесс неполон).
- Агент не меняет результаты и отчёт и не обходит остановки для человека.

Компилятор проверяет объявления до запуска и сообщает обо всех проблемах сразу:
неизвестные агенты и точки, отсутствующие и циклические зависимости, чтение ключа, которого
никто не даёт, запись в ядро, ограничения, несуществующие инструменты.

Новый процесс — `WorkflowSpec` в `workflows` плагина: основные узлы — агенты с `core=True`,
ветки через `branch`, остановки для человека — узлы с `human=True`. Процесс появляется в
`/v1/workflows` и на шкале этапов интерфейса.

### 10.6. MCP-серверы плагинов

Сервер объявляется `McpServerSpec("<id>.<имя>", register, label=...)` и в шлюзе называется
`mcp-<id>.<имя>`. Декоратор `tool` передаёт платформа: он оборачивает функцию аудитом и
помечает только для чтения; другого способа добавить инструмент нет. Последний параметр
инструмента — `audit: CallContext`, ответ — JSON. Инструмент сам проверяет границы
(контур, прогон).

### 10.7. UI-плагин

Без UI-плагина результат нового типа показывает стандартный вид из блоков `ResultView`
(`metrics`, `table`, `histogram`, `series`, `sources`), вывод агента — список строк и JSON.
UI-плагин (`ui/web/src/plugins/<id>/`) может дать собственные виды результата и выводов
агентов, заметку у денежных цифр, пояснения идентификаторов в отчёте, термины, базовый
уровень метрики изменения. При сборке `plugin.json` сверяется с манифестом установленных
плагинов (`msa-plugin ui-manifest`); сборка падает, если UI-плагин рисует неустановленный
плагин, не понимает его версию или рисует необъявленные компонент или агента.

### 10.8. Версии и совместимость

- `Plugin.sdk` — диапазон версий SDK (сейчас 1.1.0). Минорная версия SDK только добавляет.
- `Plugin.version`, `CalculationModel.version` — `x.y.z`. Прогон фиксирует версии плагинов и
  модель каждой позиции; после смены версий прогон не продолжается («код плагинов
  изменился после запуска»).
- Изменение схемы — рост `schema_version` типа (позиции старой версии отклоняются с
  объяснением). Изменение смысла метрики — новый id метрики или версия модели.
  `scenario_id` зависит от версий факторов.

### 10.9. Инструменты разработчика плагина

```powershell
uv run msa-plugin new asset <id>     # шаблон типа инструмента: модель, фактор, метрики, редактор, демо, тесты
uv run msa-plugin new agent <id>     # шаблон агента: точка расширения, MCP-инструмент, промпт, UI-вид
uv run msa-plugin check [<id>]       # проверка соответствия
uv run msa-plugin demo-run <id>      # демо-расчёт: P5/P50/P95 по позициям и срезам
uv run msa-plugin ui-manifest        # манифест UI-плагинов
```

Шаблоны сразу проходят `check`. `check` проверяет: объявления и схемы, демо-кейс (позиции из
`completes` рассчитываются, метрики в объявленных единицах, источники названы, длина
реализаций), детерминизм, независимость от порядка позиций, сборку срезов, компиляцию
процессов с агентами плагина, MCP-серверы, промпты и слова источников.

### 10.10. Критерии приёмки плагина

- [ ] Схемы `terms`/`params`/`details` с единицами из `contracts.units`, числа с источником.
- [ ] Нет молчаливых нулей и умолчаний; допущения — флагами.
- [ ] `validate` возвращает размер позиции по каждому срезу и для позиции, которая не считается.
- [ ] `calculate` читает только `prepared` и `context.scenario`; реализации потерь — во вкладе.
- [ ] Флаги, правила и разделы отчёта объявлены; числа отчёта только через `ctx.cite`.
- [ ] Агенты: `consumes` из точки, свои `produces`, осмысленные ограничения, только чтение, выключены по умолчанию.
- [ ] Демо-кейс, `msa-plugin check` зелёный, `demo-run` даёт разумные P5/P50/P95.
- [ ] Приёмочные тесты в `src/msa/plugins/<id>/tests/`.
- [ ] `lint-imports` и `test_core_boundary` зелёные; вне папок плагина нет правок.

### 11.2. MCP

Серверы работают в процессе API и вызываются по протоколу MCP через транспорт в памяти.

| Сервер | Инструменты | Кто вызывает |
|---|---|---|
| `mcp-portfolio` | `resolve_inputs`, `get_portfolio` | агент экспозиции |
| `mcp-models` | `run_model`, `list_models`, `describe_model` | агент расчёта позиции |
| `mcp-runs` | `get_run_summary`, `get_position_metrics`, `get_metric_provenance`, `describe_model` | агент объяснения |
| `mcp-<plugin_id>.<имя>` | объявленные плагином | агенты плагина, объявившие их |

Все инструменты только читают. Каждый вызов попадает в `audit_log`: прогон, узел, попытка,
инициатор (`workflow` или `llm`), `call_id`, длительность, SHA-256 аргументов и ответа,
ошибка.

## 12. Интерфейс пользователя

Браузерное приложение `ui/web` (React, Mantine) раздаётся тем же сервером API. Требования
верхнего уровня:

- **Экраны:** вход по ключу, список прогонов, запуск прогона (портфель, событие, слова о
  силе, дополнительные агенты), портфели и редактор портфеля, страница прогона.
- **Страница прогона:** шкала этапов из объявления процесса и вкладки «Сценарий и граф»
  (редактор графа и параметров, предпросмотр шока), «Позиции», «Портфель», «Отчёт» с
  решением риск-менеджера, «Источники данных», «Вопрос по результатам», «Вызовы LLM и MCP».
- **Построение из каталога:** формы редактора, подписи типов, полей, рядов и метрик
  берутся из `GET /v1/asset-types`, а не пишутся в коде.
- **Правила отображения** (`.impeccable.md`): P5/P50/P95 всегда вместе; число без
  происхождения не показывается, происхождение открывается по клику на число; красный МТС
  `#E30611` — только айдентика и действие утверждения; состояние и тяжесть риска несут
  слово или знак, а не только цвет.
- **UI-плагины** подключаются автоматически при сборке (раздел 10.7); новый UI-плагин
  требует пересборки.

## 14. Безопасность

- **Аутентификация** — персональные API-ключи (`MSA_API_KEYS`, в хранилище — SHA-256
  ключа, сравнение за постоянное время), срок действия, роль и области доступа.
- **Авторизация** — роль (раздел 3) и область контура на каждый запрос; ключ контура демо
  не читает рабочий контур.
- **Внешняя LLM** — только демо-контур; в рабочем контуре 409. Ключи внешних провайдеров —
  только в переменных окружения пользователя, не в репозитории и не в `.env`.
- **Инструменты агентов** — только чтение, только объявленные агенту, в границах прогона и
  контура; сессии БД инструментов открываются только для чтения.
- **Загрузка по URL** — только `https` и хосты из списка `MSA_INGEST_URL_HOSTS`.
- **Квоты** — на ключ: 60 прогонов и 600 вызовов агентов в час, не больше 5 одновременных
  прогонов.
- **Аудит** — все вызовы LLM и MCP, решения человека с автором и причиной.
- `.env` создаётся с уникальными локальными ключами и правами только владельца.

## 15. Надёжность, воспроизводимость, производительность

- **Воспроизводимость.** Одинаковые портфель, снимок, сценарий, зерно и версии дают те же
  числа. Реализации не зависят от состава и порядка позиций; две позиции одной бумаги
  получают одинаковые собственные шоки. Проверяется `msa-plugin check` (детерминизм,
  перестановка позиций).
- **Продолжение после сбоя.** Каждый узел пишет результат в журнал в отдельной транзакции.
  Перезапущенный процесс продолжает прогон с последнего завершённого узла без повторных
  вызовов LLM. Запись с изменившимися входами не воспроизводится (`InputsChanged`).
- **Изоляция сбоев.** Сбой позиции или агента-плагина не уничтожает остальные результаты и
  учитывается в покрытии.
- **Точность.** Погрешность P95 оценивается по репликам; невыполненный допуск отправляет
  результат на проверку ([math.md, 2.5](math.md#25-погрешность-оценки-по-репликам)).
- **Параллельность.** Очередь прогонов — 5 потоков; позиции прогона считаются ветками.
- **Объём.** Состояние прогона хранится в LangGraph и журнале; рассчитано на сотни позиций
  (нагрузочный демо-портфель `LOAD-TEST` — 50 кредитов).
- **Наблюдаемость.** Статус прогона, ожидание LLM, журнал вызовов с длительностью.

## 18. Ограничения и открытые вопросы

Архитектурные:

- Граф, сценарий, результаты и отчёт хранятся в состоянии LangGraph и журнале узлов, а не
  по ссылкам в хранилище артефактов. Достаточно для сотен позиций.
- Объяснение хранит чекпоинты в памяти на время вопроса; устойчивы ответ, журнал узла и
  аудит.
- UI-плагины проверяются при сборке, но не подгружаются динамически.
- Корреляция параметров сценария поддержана ядром (гауссова копула), но в процессе не
  задаётся: параметры независимы.

Методические (кредитная модель, нужны решения методологии):

1. Структурный параметр `elasticity` проходит проверку сценария, но расчёт его игнорирует
   (флаг `scenario_parameter_unmapped`).
2. Изменение спреда облигации пропорционально отношению PD — допущение с флагом.
3. Кредитные потери лизингополучателей не моделируются; результат лизинга всегда на
   проверке.
4. Правила осей риска не утверждены: все оси — «не оценено».
5. Залоги из профиля не участвуют в LGD: используется LGD позиции.
6. Ожидаемые потери не дисконтируются (коэффициент дисконтирования равен единице).
7. Кредитные модели считают позиции и портфели только в рублях.

Данные: калибровка PD в демо синтетическая; чувствительности акций экспертные, без
автоматической калибровки.

## 19. Направления развития

Каждая очередь начинается с экономического контракта владения; признаки («голубая фишка»,
IPO, токенизация) не создают новый тип, пока не меняют расчёт.

| Очередь | Семейства | Что добавить в платформу |
|---|---|---|
| 1 | деньги, валюты, депозиты, обычный долг | денежные потоки, начисления, кривые ставок; артефакты по ссылкам |
| 2 | ETF, ПИФ, REIT, фонды фондов | доли и NAV, вложенные портфели без двойного счёта |
| 3 | физические товары, спотовые цифровые активы | количество и единицы, хранение, издержки |
| 4 | форварды, фьючерсы, РЕПО, свопы | несколько ног, обеспечение и маржа, контрагенты |
| 5 | опционы, конвертируемые и структурированные продукты | нелинейная переоценка, волатильность |
| 6 | ABS/MBS/CDO/CLO | пулы, транши, waterfall, зависимые дефолты |
| 7 | недвижимость, инфраструктура, private equity | проектные потоки, обязательства финансирования |
| 8 | страхование, пенсионные требования | сценарные выплаты, актуарные предпосылки |
| 9 | коллекционные активы, сложные DeFi-позиции | оценочные модели, протокольные риски |

Агентная часть: обоснование связей инструментами (фрагменты документа, аналоги),
сравнение вариантов сценария, подбор данных при пробелах — агентами-плагинами в
существующих точках или отдельными процессами.

## 20. Глоссарий

| Термин | Значение |
|---|---|
| Ядро | всё в `src/msa/` и `ui/web/src/` вне папок плагинов |
| Плагин | папка `src/msa/plugins/<id>/` и, по желанию, `ui/web/src/plugins/<id>/` с объявлением `Plugin` |
| Контур | демо или рабочий: разные данные, схемы БД и допустимые LLM |
| Граф события | «событие → канал → отрасль → фактор»; не путать с графом выполнения LangGraph |
| Фактор | величина, которую двигает сценарий и читает модель (`FactorSpec`) |
| Параметр сценария | распределение изменения одного фактора (`MacroParameter`) |
| Реализация | одна точка совместной матрицы сценариев |
| Срез | мера портфеля с одним смыслом (`credit.loss`, `market.pnl`) |
| Снимок данных | неизменяемый набор данных на дату (`DataSnapshot`) |
| Дерево метрик | адресуемые числа прогона, на которые ссылается отчёт |
| Точка расширения | место процесса, куда подключаются агенты плагинов |
| P5/P50/P95 | 5-й, 50-й и 95-й процентили распределения |
| ES95 | ожидаемый дефицит: средние потери в худших 5 % реализаций |
| PD, LGD, EAD, EL | вероятность дефолта, доля потерь при дефолте, сумма под риском, ожидаемые потери |
| ICR | покрытие процентов операционной прибылью |
| V1–V11 | правила проверки ответа LLM, отчёта и прогона |
