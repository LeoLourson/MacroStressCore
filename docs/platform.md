# Платформа расширяемых расчётов и агентов

MacroStress — модульный монолит. Ядро не знает типов инструментов и конкретных агентов.
Оно даёт общие возможности: данные на дату оценки, общий сценарий, диспетчер моделей,
агрегацию по срезам, отчёт с проверяемыми числами, процессы LangGraph с остановками для
человека, MCP и аудит. Всё предметное — кредит, акции, валютный фактор, объяснение,
исследовательские агенты — подключается плагинами. Как написать плагин — в
[plugins.md](plugins.md). Здесь описаны контракты и устройство ядра.

## 1. Модель предметной области

```
Party (эмитент, контрагент: ОКВЭД, страна)
  └─ Instrument (instrument_type, currency, terms по схеме типа, schema_version, issuer_id)
       └─ Position (params по схеме типа, model_id — явный выбор модели или умолчание типа)
Portfolio (base_currency, as_of, snapshot_id)          ── PortfolioBundle: всё вместе
DataSnapshot (as_of, items: SnapshotItem)               ── данные на дату оценки
ScenarioSpec (параметры факторов, граф события)          ── подтверждает аналитик
CalculationResult (одна позиция) → AggregationContribution → SliceResult → PortfolioResult
```

- `contracts/domain.py`: `Party`, `Instrument`, `Position`, `Portfolio`,
  `PortfolioBundle` (проверка ссылок), `PositionContext` — позиция с инструментом и
  эмитентом, как её читает прогон.
- `terms` и `params` проверяются по схемам типа из реестра (`check_bundle`, валидатор
  V2). Неизвестный тип, чужая версия схемы и лишнее поле отклоняются с объяснением.
- Единицы (`contracts/units.py`): простые (`fraction`, `days`, `ratio`, `shares`,
  `log_return`, …), деньги `<CCY>_million`, цены `<CCY>_per_unit`. Каждое число с
  источником — `Parameter(value, unit, evidence)`; `Evidence` — документ, историческая
  оценка или допущение эксперта с автором и датой.

## 2. Снимок данных

`DataSnapshot(snapshot_id, as_of, items)`. Элемент — `SnapshotItem(item_id, kind, subject,
observed_on, values, attributes, evidence)`: цена бумаги, курс пары, отчётность эмитента,
чувствительности, дивиденды. Снимок неизменяем: повторная загрузка того же содержимого ничего
не меняет, другое содержимое под тем же id отклоняется (409). Элемент позже `as_of`
снимка отклоняется при загрузке.

Модель объявляет, какие данные ей нужны (`DataRequirement`). Платформа выбирает для
каждого требования последний элемент **не позже даты оценки прогона** и записывает
причину для всего, что не нашлось:

- `missing` — данных нет;
- `dated_after_as_of` — данные есть, но датированы после даты оценки и не используются.

Аналоги (`peers_of`) подбираются по глубине совпадения ОКВЭД. В прогоне данные читает
`mcp-portfolio.resolve_inputs`: каждый вызов проходит через аудит и ограничен портфелем
прогона. API: `GET/POST /v1/{demo/}snapshots`, `GET /v1/{demo/}snapshots/{id}?kind=…`.

## 3. Сценарий и общие реализации

Реестр факторов заменяет прежний закрытый список из семи драйверов. Фактор
(`FactorSpec`) объявляет плагин: `credit.revenue`, `equity.market`, `market.fx`, …
Параметр сценария (`MacroParameter`) двигает один фактор:

- **через граф** (`scope="graph"`): параметр входит в канал графа события и доходит до
  позиции через отрасль её эмитента и узел фактора (`kind="factor"`), с эластичностями и
  лагами рёбер;
- **напрямую по ключу** (`global`, `sector`, `instrument`, `currency_pair`): индекс рынка,
  отраслевой ключ, бумага, валютная пара `CCY/BASE`.

`ScenarioSet` — подтверждённые распределения. Реализации генерируются **один раз на
прогон**: R независимо перемешанных реплик Соболя по N точек, столбцы в отсортированном
порядке имён параметров. Все позиции читают одну и ту же матрицу. Собственные шоки
позиций (остаточный риск акции) генерируются из отдельного потока:
`seed = sha256(run_seed:subject:name)`. Поэтому они не зависят от состава и порядка
позиций, и две позиции одной бумаги получают одинаковые реализации.

`scenario_id` — хеш спецификации сценария, seed, даты оценки, горизонта, графа, версий
факторов и хеша матрицы. Он есть в каждом результате. Вклады в срез с другим
`scenario_id` не принимаются.

## 4. Расчёт позиции: диспетчер

`engine/dispatch.py`, `engine/runner.py`. Для каждой позиции:

1. **Проверка схем** `terms`/`params`/`schema_version`.
2. **`model.requirements()`** → разрешение по снимку (или через `mcp-portfolio`).
3. **`model.validate(prepared)`** → `Diagnostics`: ошибки, размеры позиции по срезам,
   собственные шоки. Ошибка даёт `execution="not_run"` с причиной и размером для
   покрытия.
4. **`model.calculate(prepared, context)`**. В прогоне это вызов
   `mcp-models.run_model(model_id, payload)`: модель получает подготовленные входы и
   спецификацию сценария, а платформа пересоздаёт реализации и сверяет `scenario_id`.
5. **Проверка выхода** (`output_problems`): идентичность результата, объявленные метрики и
   единицы, обязательные метрики, форма распределений, срез, единица и длина реализаций
   вклада, схема `details`.

Исключение модели становится результатом `failed` с флагом `model_error:<Тип>`. Сбой одной
позиции не уничтожает остальные результаты и учитывается в покрытии.

### Конверт результата

`CalculationResult` — общий конверт для любой модели:

| Поле | Смысл |
|---|---|
| `position_id`, `instrument_id`, `instrument_type`, `plugin_id/version`, `model_id/version` | что и чем посчитано |
| `as_of`, `horizon`, `seed`, `base_currency`, `scenario_id`, `snapshot_id`, `macro_draws_sha256` | на чём |
| `execution` | `completed`, `not_run`, `failed` — был ли расчёт |
| `status`, `applicability`, `data_quality` | насколько результату можно доверять |
| `metrics` | `MetricValue`: значение и/или P5/P50/P95 (+ES95) в объявленной единице |
| `details`, `details_schema` | собственный результат модели; показывается её видом |
| `input_sources`, `sources`, `assumptions`, `flags`, `diagnostics`, `limits` | происхождение и ограничения |
| `contributions` | `AggregationContribution` во срезы: мера, единица, горизонт, размер, допуск, реализации |

## 5. Срезы портфеля

`engine/aggregation.py`. Срез (`SliceSpec`) — одна мера с одним смыслом. Сейчас их два:
`credit.loss` (рост ожидаемых кредитных потерь, база покрытия — EAD) и `market.pnl`
(рыночные потери стоимости, база — стоимость позиций).

- Потери допущенных позиций складываются **внутри каждой реализации**, и только потом
  считаются квантили, ES95, VaR95. Сумма P95 по позициям показывается отдельно: разница с
  P95 среза — эффект диверсификации.
- Срезы между собой **не складываются**.
- Покрытие считается на базе среза по всем позициям прогона, которые к нему относятся,
  рассчитанным и нет. Если размер позиции нельзя измерить, срез становится `incomplete`.
  Если непокрытая доля выше `coverage_limit`, срез тоже `incomplete`.
- Допуск вклада: `included`; `admitted:<правило>` — результат `needs_review`, допущенный
  утверждённым правилом включения с раскрытием; `excluded:<причина>`.
  `incompatible:<причина>` означает другую единицу, горизонт или `scenario_id`.
- `PortfolioResult.not_aggregated` — позиции вне всех срезов, с причиной.

## 6. Отчёт и происхождение чисел

- **Дерево метрик** (`reporting/tree.py`) — единый адресуемый вид чисел прогона:
  `/positions/<id>/metrics/<metric>/p50`, проекции плагинов (`/positions/<id>/covenants/…`),
  `/portfolio/slices/<id>/loss_quantiles/p95`, `…/covered_percent`. Его читают отчёт,
  валидатор V9, экраны, трасса и MCP.
- **Отчёт** (`reporting/builder.py`) собирается из общих разделов (итог по срезам,
  рекомендации, ограничения, допущения) и разделов плагинов. Разделы пишут числа только
  через `ReportContext.cite`. V9 сверяет каждое число текста с деревом метрик.
- **Рекомендации** — таблица правил плагинов (`RecommendationRule`) над наблюдениями.
  Пороги в силе хранятся в журнале `rule_threshold`; без утверждённого значения действует
  порог объявления, и отчёт это раскрывает.
- **Трасса** (`/trace`) показывает для каждого числа отчёта значение, узлы и источники:
  данные позиции, фрагменты события на пути к её отрасли и параметры сценария, которые до
  неё дошли.

## 7. Процессы, агенты, журнал

- **Процесс** — `WorkflowSpec`, данные плагина `core`: `stress_test` и `explain_results`.
  Компилятор (`graph/compiler.py`) собирает граф LangGraph, вставляет агентов плагинов по
  точкам расширения и проверяет объявления.
- **Состояние.** Ключи ядра — `RunState`. Агенты плагинов пишут только в
  `extensions[<agent_id>]`. Основные артефакты (граф, сценарий, результаты, отчёт)
  хранятся в состоянии LangGraph и в журнале узлов, по ссылкам не выносятся (см.
  «Отклонения»).
- **Журнал узлов** (`run_node_result`). Ключ — узел или ветка (`quant_agent/<позиция>`,
  `explain/<id>`) плюс попытка (ревизия сценария). Запись хранит версию агента и хеш
  прочитанных входов. Перезапуск процесса продолжает прогон с последнего завершённого
  узла без повторных вызовов LLM. Запись с другими входами не воспроизводится
  (`InputsChanged`).
- **Человек в контуре.** Подтверждение графа и сценария (`human_fix_graph`) и решение по
  отчёту (`human_approval`: утвердить, вернуть с причиной, отклонить с причиной). Ни одна
  точка расширения не лежит на пути в обход них.
- **Фиксация кода.** Прогон записывает версии плагинов и модель каждой позиции. После смены
  версий он не продолжается.

## 8. Объяснение результатов

`POST /v1/{demo/}runs/{id}/explanations {"question": …}` задаёт вопрос о рассчитанном
прогоне (без результатов — 409). В рабочем контуре внешняя LLM не допускается (409). Ответ
готовит процесс `explain_results` в фоне; `GET …/explanations[/{explanation_id}]`.

- Агент (`agents/explain.py`) — ограниченный цикл LLM ↔ инструменты: не больше 6 шагов
  модели и 12 вызовов.
- Инструменты `mcp-runs`: `get_run_summary`, `get_position_metrics`,
  `get_metric_provenance`, `describe_model`. Все только читают и привязаны к прогону
  вызова. Модель не видит `run_id`: его подставляет агент.
- Каждое число ответа ищется в ответах инструментов (как есть, с округлением, ×100 для
  долей). Непроверенные числа получают одну попытку исправления. Если после неё числа не
  подтвердились, модель не вызывает инструменты (заглушка, `MSA_LLM_TOOL_CALLING=0`) или
  исчерпаны лимиты, ответ собирается из сводки прогона без модели (`mode="structured"`),
  и причина раскрывается.
- Вызовы LLM и инструментов записываются в аудит под узлом `explain/<id>` прогона, с
  инициатором `llm`.

## 9. MCP и аудит

Серверы работают в процессе API и вызываются по протоколу MCP через in-memory транспорт
(`mcp/gateway.py`):

| Сервер | Инструменты | Кто вызывает |
|---|---|---|
| `mcp-portfolio` | `resolve_inputs`, `get_portfolio` | exposure-агент |
| `mcp-models` | `run_model`, `list_models`, `describe_model` | quant-агент |
| `mcp-runs` | `get_run_summary`, `get_position_metrics`, `get_metric_provenance`, `describe_model` | агент объяснения (LLM) |

Каждый вызов попадает в `audit_log`: прогон, узел, попытка, инициатор (`workflow` | `llm`),
`call_id` модели, длительность, SHA-256 аргументов и ответа, ошибка. Сессии чтения
открываются в режиме «только чтение» с ролью контура. Вызов не может приписать себя
прогону чужого контура.

## 10. HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/asset-types` | каталог плагинов: типы (схемы, форма редактора, модели, вид), метрики, факторы, срезы, действия, правила, флаги, единицы |
| GET | `/v1/models`, `/v1/factors`, `/v1/slices`, `/v1/workflows` | каталоги моделей, факторов, срезов; процессы с этапами, точками и агентами |
| GET/POST | `/v1/{demo/}portfolios`, `…/{id}`, `…/{id}/names` | портфели как бандлы Party/Instrument/Position |
| POST | `/v1/demo/portfolios/draft` | портфель из редактора: строки → бандл и снимок аналитика |
| GET/POST | `/v1/{demo/}snapshots`, `…/{id}` | снимки данных |
| GET/POST | `/v1/{demo/}runs` | список и запуск: `portfolio_id`, `event`, `workflow_id`, `as_of`, `snapshot_id`, `models`, `agents`, `position_ids` |
| GET | `/v1/{demo/}runs/{id}`, `/artifacts`, `/report`, `/trace`, `/activity` | статус, артефакты, отчёт, происхождение, вызовы LLM и MCP |
| POST | `/v1/{demo/}runs/{id}/resume` | подтверждение графа и сценария или решение по отчёту |
| POST/GET | `/v1/{demo/}runs/{id}/explanations[/{eid}]` | вопросы по результатам |
| POST | `/v1/{demo/}documents`, `/v1/{demo/}scenario-check` | событие; проверка черновика графа и сценария |

Прогон фиксирует процесс и его версию, позиции, модели, снимок и сценарий. Эти поля
возвращают `status` и `artifacts`.

## 12. Интерфейс

`ui/web` строится из каталога. Шкала этапов берётся из процесса прогона; вкладки:
«Сценарий и граф», «Позиции» (группы по типу, у каждого типа свои показатели), «Портфель»
(срезы, дополнительные агенты), «Отчёт», «Происхождение чисел», «Вопрос по результатам»,
«Вызовы LLM и MCP». Редактор портфеля строит формы по объявлению типа. Результат позиции
показывает компонент UI-плагина или стандартный вид из блоков `ResultView`. Совместимость
UI-плагинов с серверными проверяется при сборке ([plugins.md §5](plugins.md#5-ui-плагин-собственный-экран-результата)).

## 14. Исправления аудита

Исправлено при переходе на платформу (находки `docs/asset-extension-mcp-audit.md` и
`docs/audit.md`):

| Находка | Исправление |
|---|---|
| A1 — отсутствующие признаки PD молча исключались | калиброванный PD без обязательного признака — ошибка; необязательные признаки объявлены явно (`PDCalibration.optional_features`) |
| A2 — дата расчёта не ограничивала данные | все данные приходят из снимка на `as_of`; будущие элементы отклоняются с причиной |
| A3 — единица ковенанта всегда ratio | единица ковенанта берётся из ряда показателя |
| A4 — границы `fraction` игнорировались | объявленные границы пересекаются с [0, 1] и проверяются |
| A5 — неполный результат плагина без причины | `output_problems` сверяет выход модели с объявлением |
| A6 — рекомендации и отчёт расширялись не полностью | правила, действия, наблюдения, разделы отчёта и слова флагов объявляет плагин |
| LLM без инструментов | tool-calling в клиенте LLM, `mcp-runs`, объяснение результатов |
| #8 — английская причина по рыночной оси | причина по-русски |
| #9 — нет списка рабочих портфелей | `GET /v1/portfolios`; интерфейс показывает список в обоих контурах |

Не исправлено, нужно методическое решение (`docs/audit.md`): F07 — покрытие и HHI по
затронутым событием позициям, а не по всему портфелю; вырождение PD при EBITDA ≤ 0;
структурный параметр `elasticity` без использования; флоатер как фиксированный купон;
кредитные потери лизингополучателей; неутверждённые правила осей риска; залоги вне LGD.

## 15. Отклонения от плана и известные ограничения

- **Состояние по ссылкам.** План предлагал хранить большие артефакты ядра по ссылкам.
  Сейчас граф, сценарий, результаты и отчёт лежат в состоянии LangGraph и журнале узлов.
  В пространство имён вынесены только выводы плагинов. Для текущих объёмов (сотни позиций)
  этого достаточно; вынос в хранилище артефактов запланирован вместе с первой очередью
  денежных инструментов.
- **Качество данных пересчитывается в каждом прогоне** по отчётности снимка, а не берётся
  из каталога. Поэтому эталонное сравнение Track A не включает `coverage.input_data`.
- **Флаг `factor_not_reached`** заменил прежний `driver_not_reached`. Повторяющиеся флаги
  больше не дублируются.
- **Объяснение** хранит чекпоинты процесса в памяти на время одного вопроса: у него нет
  остановок для человека. Устойчивы ответ, журнал узла и аудит вызовов.
- **UI-плагины** проверяются на совместимость при сборке, но не подгружаются динамически:
  новый UI-плагин требует пересборки `ui/web`.

## 16. Дорожная карта

Каждая очередь начинается с экономического контракта владения. Признаки («голубая фишка»,
IPO, токенизация) не создают новый тип, пока не меняют расчёт.

| Очередь | Семейства | Что развивать в платформе |
|---|---|---|
| 1 | деньги, валюты, депозиты, обычный долг | денежные потоки, начисления, кривые ставок, погашения; артефакты по ссылкам |
| 2 | ETF, ПИФ, REIT, фонды фондов | доли и NAV, вложенные портфели, look-through без двойного счёта |
| 3 | физические товары, спотовые цифровые активы | количество и единицы, хранение, издержки, рыночная ликвидность |
| 4 | форварды, фьючерсы, РЕПО, свопы | несколько ног, обеспечение и маржа, контрагенты |
| 5 | опционы, конвертируемые и структурированные продукты | нелинейная переоценка, волатильность, события исполнения |
| 6 | ABS/MBS/CDO/CLO, кредитные структуры | пулы, транши, waterfall, зависимые дефолты |
| 7 | недвижимость, инфраструктура, private equity, роялти | проектные потоки, оценочные даты, обязательства финансирования |
| 8 | страхование, пенсионные требования | сценарные выплаты, актуарные предпосылки |
| 9 | коллекционные активы, NFT, сложные DeFi-позиции | оценочные модели, ликвидность, составные права, протокольные риски |

Агентная часть: обоснование каузальных связей инструментами (фрагменты документа,
аналоги), сравнение вариантов сценария по запросу, подбор данных при пробелах. Каждое из
этих расширений — агент-плагин в существующей точке или отдельный процесс.
