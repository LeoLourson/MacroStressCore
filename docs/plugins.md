# Расширение платформы: типы инструментов, расчёты, агенты

Платформа расширяется плагинами. Плагин — папка `src/msa/plugins/<plugin_id>/` (пакет с
объявлением `plugin = Plugin(...)`, его тесты, демо-данные, промпты и README) и, по
желанию, папка `ui/web/src/plugins/<plugin_id>/` с его экранами. Платформа находит плагин
при старте и проверяет объявление целиком. Ядро — всё остальное в `src/msa/` и
`ui/web/src/` — при этом не меняется. Если для нового плагина пришлось править ядро,
значит, в SDK не хватает точки расширения. Такой случай обсуждается как изменение SDK, а не
как часть плагина (раздел 8).

## 1. Что можно расширить

| Что добавить | Что объявить в `Plugin` | Где появится без правки ядра |
|---|---|---|
| Тип инструмента (акция, депозит, фьючерс) | `instrument_types` (`InstrumentTypeSpec`) | каталог `/v1/asset-types`, проверка портфеля, редактор портфеля, MCP |
| Расчётную модель | `models` (`CalculationModel`) | диспетчер, `mcp-models.run_model`, `/v1/models`, выбор модели в запросе прогона |
| Метрику | `metrics` (`MetricSpec`) | результат, дерево метрик, отчёт, экраны, объяснение |
| Фактор сценария | `factors` (`FactorSpec`) | сценарий аналитика, граф события, промпт causal-агента, `/v1/factors` |
| Срез портфеля | `slices` (`SliceSpec`) | агрегатор, вкладка «Портфель», отчёт |
| Вид данных снимка | `snapshot_kinds` (`SnapshotKindSpec`) | импорт снимка, каталог |
| Экран результата | `views` (`ResultView`) + UI-плагин по желанию | ящик позиции на вкладке «Позиции» |
| Разделы отчёта | `report_sections`, `tree` | текст отчёта с проверяемыми числами (V9) |
| Правила рекомендаций | `observations`, `rules`, `actions` | рекомендации отчёта, журнал порогов |
| Слова флагов | `flags`, `informational_flags` | отчёт, экраны, MCP |
| Параметры контура | `run_options`, `notes` | модели получают их в `RunOptions.options`; отчёт раскрывает `notes` |
| Агента | `agents` (`AgentPlugin`) | точка расширения процесса, журнал, аудит, экран «Вызовы LLM и MCP» |
| MCP-сервер с инструментами для агентов | `mcp_servers` (`McpServerSpec`) | шлюз MCP с аудитом; инструменты видят только агенты, объявившие их |
| Промпт агента | `prompts` и файл `prompts/<name>-v<N>.txt` | `msa.plugin_sdk.prompts.prompt("<plugin_id>.<name>")` |
| Процесс (workflow) | `workflows` (`WorkflowSpec`) | компилятор LangGraph, `/v1/workflows`, шкала этапов в интерфейсе |
| Слова источников и авторов данных | `sources`, `authors` | отчёт, каталог, вкладка «Источники данных», происхождение чисел |
| Демо-данные для стенда | папка `demo_data/` плагина | демо-портфели и демо-снимок (`demo/catalog.py`) |
| Экран результата, вывода агента, термины | UI-плагин: `views`, `agents`, `glossary`, `glosses`, `notes`, `baseline` | вкладки «Позиции», «Портфель», «Отчёт» |

Идентификаторы метрик, факторов, срезов, моделей, правил, видов, разделов, агентов,
MCP-серверов и промптов начинаются с `<plugin_id>.`: `equity.pnl`, `credit.loss`,
`research.notes`. Поэтому два плагина могут использовать одинаковые короткие имена.
Глобальны только идентификаторы типа инструмента, вида данных снимка, действия и процесса.
Их уникальность проверяет реестр.

## 2. Быстрый старт: `msa-plugin`

```powershell
uv run msa-plugin new asset gold --label "Золото"          # src/msa/plugins/gold/
uv run msa-plugin new agent watcher --point before_report   # src/msa/plugins/watcher/
uv run msa-plugin check gold                                # проверка соответствия
uv run msa-plugin demo-run gold                             # демо-расчёт: P5/P50/P95 по позициям и срезам
uv run msa-plugin check                                     # все установленные плагины
uv run msa-plugin ui-manifest                               # манифест для сборки UI (раздел 5)
```

`new` создаёт плагин, который **сразу проходит** `check`, в раскладке раздела 8. Шаблон
актива содержит тип инструмента, модель, фактор, две метрики, форму редактора, демо-кейс,
`tests/`, `demo_data/` и `README.md`. Шаблон агента содержит агента, подключённого к точке
расширения и выключенного по умолчанию, его MCP-сервер с инструментом только для чтения,
промпт в `prompts/`, `tests/`, `README.md` и вид вывода агента в
`ui/web/src/plugins/<id>/`. Шаблон можно создать вне репозитория (`--dest DIR`: пакет в
`DIR/<id>`, UI в `DIR/ui/<id>`) и проверять его там же (`check --path DIR/<id>`). Пакет в
`src/msa/plugins/` платформа подключает при следующем старте; его тесты `pytest` собирает
вместе с тестами платформы.

Дальше шаблон заменяется своим содержимым шаг за шагом: после каждого шага `check` должен
оставаться зелёным.

## 3. Новый тип инструмента и его расчёт

### Контекст причинного агента

Причинный агент получает контекст выбранных моделей портфеля из реестра плагинов:
тип инструмента, описание модели, ОКВЭД (если он есть), горизонт, требования
`CalculationModel.requirements` и полные объявления `FactorSpec`. Поэтому добавление
типа актива не требует править промпт или добавлять ветку по имени типа в ядре.
Денежные суммы позиции и данные снимка в этот контекст не передаются.

Объявляйте смысл фактора в `description`, его `scope`, `unit`, `application`,
`quantity` и `temporal`, а точный ключ для каждой позиции возвращайте через
`FactorRequirement`. Требование должно ссылаться на фактор из `model.factors`.
Агенту доступны только факторы моделей текущего портфеля: наличие кредитного плагина
не добавляет кредитные факторы в граф портфеля акций.

Для `scope="graph"` граф передаёт шок через канал и отрасль. Для остальных областей
применения узел фактора содержит `factor` и `key`, а путь может идти от канала прямо
к фактору, без ОКВЭД. Такие связи объясняют механизм; их эластичности и задержки
не умножают прямой шок. Его величину в объявленных единицах читает модель.
Например, прямой фактор нового плагина с `unit="fraction"` получает снижение на
пятнадцать процентов как `-0.15`, с `unit="log_return"` — как `ln(0.85)`.

Если событие указывает влияние на фактор, но не задаёт величину, LLM оценивает её сама
диапазоном (треугольное распределение) и помечает параметр как оценку. Сервер записывает
такой параметр как допущение с автором `LLM:<модель> (оценка модели)` и датой. Аналитик
видит его на вкладке сценария с пометкой «Допущение», а в отчёте его автор указан в разделе
«Допущения и авторы». Если аналитик меняет величину параметра, автором допущения
становится он, будь то оценка модели или число из текста; параметр, добавленный аналитиком,
записывается как его допущение с источником «сценарий, заданный аналитиком». Вкладка
сценария показывает это авторство ещё до подтверждения. Параметр, не покрывший затронутый фактор, возвращается LLM на
исправление. Проверяются все затронутые факторы, даже если один уже задан.
Явный нулевой сценарий допустим; отсутствие параметра не означает нулевой риск.
Неизвестный фактор, чужой ключ и неверная единица в ответе LLM отклоняются.

Новая математика остаётся ответственностью плагина. Платформа не переводит рост
издержек в падение цены или вероятность дефолта без модели либо явного допущения.
Промпты отчёта и объяснений используют смысл метрик и разделы плагинов, не навязывая
кредитные разделы. Сквозной пример независимого типа актива без эмитента и без
кредитных плагинов проверяется в `tests/platform/test_causal_plugins.py`.

### 3.1. Сначала экономический контракт

До кода нужно ответить на три вопроса:

- **Чем владеет портфель.** Это задаёт `terms` инструмента и `params` позиции. «Голубая
  фишка», «высокодоходная», IPO — признаки или события, а не новый тип, если способ расчёта
  не меняется. Токенизация сама по себе тоже не создаёт новый способ оценки.
- **Какие данные на дату оценки нужны модели.** Цена, курс, кривая, отчётность,
  чувствительности. Эти данные приходят в снимке (`DataSnapshot`), а не в позиции.
- **Во что превращается результат.** Метрики и вклад позиции в срез портфеля (потери в
  деньгах базовой валюты на горизонте).

### 3.2. Схемы: `terms`, `params`, `details`

Схемы — pydantic-модели с `extra="forbid"` (`msa.contracts.common.Contract`). Каждое число
с источником — `Parameter` (`value`, `unit`, `evidence`): без источника его не принять.

```python
from msa.contracts.common import Contract, Identifier, Number
from msa.contracts.evidence import Parameter

class Terms(Contract):          # Instrument.terms
    driver_key: Identifier
    beta: Number

class Position(Contract):       # Position.params
    quantity: Parameter         # unit "count" — проверяется валидатором модели

class Details(Contract):        # CalculationResult.details
    price: Number
    value_current: Number
```

Правила:

- Единицы — только из `msa.contracts.units`: `fraction`, `days`, `ratio`, `shares`,
  `log_return`, деньги `<CCY>_million`, цены `<CCY>_per_unit`. В объявлениях метрик и полей
  можно писать `base_money`: это миллионы базовой валюты портфеля, конкретная единица
  подставляется в прогоне.
- **Никаких молчаливых умолчаний.** Отсутствующее значение либо обязательно, либо имеет
  объявленное умолчание с флагом допущения (`EditorField.assumption`), и этот флаг доходит
  до результата. Ноль дивидендов или остаточного риска задаётся явно.
- Изменили схему — увеличьте `schema_version` типа. Позиции старой версии отклоняются с
  объяснением, а не читаются молча.

### 3.3. Модель: `requirements` → `validate` → `calculate`

Модель — наследник `CalculationModel` из трёх шагов. Модель **чистая**: она не обращается
к БД, сети и LLM и видит только подготовленные входы и сценарий. Всё остальное делает
платформа.

```python
class Model(CalculationModel):
    model_id = "gold.model.v1"
    version = "0.1.0"
    instrument_types = ("gold_position",)
    metrics = ("gold.value_current", "gold.loss")
    required_metrics = metrics
    slices = ("market.pnl",)
    factors = ("gold.driver",)
    details_schema = Details

    def requirements(self, position, options):
        """Что нужно из снимка и какие факторы. Данные ещё не прочитаны."""

    def validate(self, prepared) -> Diagnostics:
        """Суждение о подготовленных входах: ошибки, размеры позиции по срезам,
        собственные шоки позиции."""

    def calculate(self, prepared, context) -> CalculationResult:
        """Результат на общих реализациях сценария."""
```

**`requirements(position, options)`** возвращает `DataRequirements`:

- `DataRequirement(key, kind, subject | subjects | peers_of, required, many, ...)` —
  элементы снимка. Платформа берёт последний элемент **не позже `as_of`**. Будущие данные
  не используются: позиция получает `data_dated_after_as_of:<key>`. Отсутствующие данные
  дают `data_missing:<key>`. `peers_of` подбирает компании-аналоги по глубине совпадения
  ОКВЭД.
- `FactorRequirement(factor_id, key)` — факторы, к которым позиция чувствительна.
  Отсутствие фактора в сценарии модель должна раскрыть флагом
  `factor_not_in_scenario:<factor>:<key>`.
- Для инструмента в чужой валюте используйте базовый плагин `market`:
  `msa.plugins.market.fx.requirement(currency, base)` добавляет курс, `fx.factor(...)` —
  валютный фактор пары `CCY/BASE`, `fx.log_change(...)` — его реализации.

**`validate(prepared)`** возвращает `Diagnostics`:

- `items` — `Diagnostic(code, severity, message, path)`. Любая `error` останавливает
  позицию: `execution="not_run"`, статус из `blocked_status` (`needs_review` или `invalid`).
  Коды становятся флагами результата; их слова объявляются в `Plugin.flags`.
- `exposures` — размер позиции на базе каждого среза (`None`, если его нельзя измерить).
  Размер нужен **и когда позиция не считается**: иначе её доля выпадет из покрытия
  незаметно. Неизмеримый размер делает срез `incomplete`.
- `idiosyncratic` — собственные шоки позиции `IdiosyncraticFactor(name, subject, sigma)`.
  Платформа генерирует их из отдельного детерминированного потока по `seed` и `subject`.
  Поэтому две позиции одной бумаги получают одинаковые реализации, и порядок позиций на
  результат не влияет.

**`calculate(prepared, context)`** читает сценарий только через
`context.scenario` (`ScenarioView`):

- `parameters_for(factor_id, key)` — имена параметров сценария, которые двигают фактор;
- `draws(name)` — реализации параметра формы `(replicates, points)`, общие для всех позиций;
- `central(name)` — управленческое центральное значение;
- `idiosyncratic(name)` — реализации собственного шока.

Результат собирается хелпером `envelope()`: он заполняет идентичность результата (позиция,
модель, версии, `scenario_id`, `snapshot_id`, хеш матрицы, хеш кода). Модель указывает
только то, что посчитала:

```python
from msa.plugin_sdk.results import distribution, envelope, scalar

return envelope(prepared, context, self, plugin_id="gold", plugin_version="0.1.0",
    status="ok",
    metrics={
        "gold.value_current": scalar("gold.value_current", unit, value0),
        "gold.loss": distribution("gold.loss", unit, losses, value=central_loss, tail=True),
    },
    details=Details(...).model_dump(mode="json"),
    input_sources={"price": [...]},            # какие данные снимка прочитаны
    sources=list(price.evidence),              # на чём основаны числа
    flags=flags,
    contributions=[AggregationContribution(
        slice_id="market.pnl", measure="gold.loss", unit=unit, horizon=context.horizon,
        scenario_id=context.scenario.scenario_id, exposure=value0,
        exposure_basis="market_value", draws=losses.tolist())],
)
```

- `distribution(..., tail=True)` даёт P5/P50/P95 и ES95. Квантили всегда показываются
  вместе.
- `contributions[].draws` — потери позиции в **каждой** реализации (длина
  `points × replicates`) в деньгах базовой валюты. Агрегатор складывает их внутри
  реализаций и только потом берёт квантили. Положительное значение — потеря.
- Исключение внутри `calculate` не роняет прогон: диспетчер превращает его в результат
  `failed` с флагом `model_error:<Тип>`, остальные позиции считаются дальше.
- Диспетчер сверяет выход с объявлением (`output_problems`): идентичность результата, только
  объявленные метрики в объявленных единицах, распределение там, где объявлено
  распределение, обязательные метрики, срез, единица и длина реализаций вклада, схема
  `details`. Нарушение делает результат недействительным с названной причиной.

Общие вычисления платформы модель берёт из `msa.plugin_sdk.calc`: общие реализации
сценария (`ScenarioSet`, `estimate`), сигнал фактора через граф (`factor_signal`,
`factor_change`), проверку области значений (`check_domain`), `expected_shortfall`, вклады
Шепли (`shapley_exact`, `shapley_contributions`), `data_quality_level`, `worst`,
`code_sha256`. Для разделов отчёта — `msa.plugin_sdk.report` (`pointer_token`,
`extract_numbers`, `sentence`). Модули `msa.engine`, `msa.reporting` и другие модули ядра
плагин не импортирует (раздел 8).

Подробные примеры: `plugins/equity/model.py` (факторный стресс, FX, собственный шок,
вклады Шепли, гистограмма потерь) и `plugins/credit/model.py` (адаптер к помесячной модели
заёмщика).

### 3.4. Факторы: через граф или напрямую

| `scope` | Как фактор попадает в позицию | Пример |
|---|---|---|
| `graph` | параметр входит в канал графа события и через отрасль (ОКВЭД) доходит до узла `kind="factor"` | `credit.revenue`, `credit.cogs`, `equity.sector` |
| `global` | напрямую по ключу, одинаково для всех | `equity.market` с ключом `MOEX` |
| `sector` | напрямую по отраслевому ключу | отраслевой фактор с ключом вроде `oil_gas` |
| `instrument` | напрямую по идентификатору инструмента | собственный фактор бумаги |
| `currency_pair` | напрямую по паре `CCY/BASE` | `market.fx` с ключом `USD/RUB` |

`application` (`relative` / `additive` / `log`) и `quantity` описывают, как шок меняет
величину, а `unit` — в чём задан параметр сценария. Графовые факторы автоматически
попадают в промпт causal-агента, в редактор графа и в проверку сценария. Прямые факторы
аналитик задаёт в сценарии с ключом. Модель читает все параметры фактора через
`parameters_for(factor_id, key)` и суммирует их.

### 3.5. Срезы портфеля

Срез — одна мера с одним экономическим смыслом, суммируемая по реализациям:

```python
SliceSpec("market.pnl", "Рыночный результат", measure_label="Рыночные потери",
          exposure_basis="market_value", exposure_label="Стоимость позиций",
          coverage_limit=0.05)
```

- Срезы **никогда не складываются между собой**: кредитные потери (база EAD) и рыночный
  результат (база стоимости) показываются отдельно.
- Если непокрытая доля базы выше `coverage_limit`, срез получает статус `incomplete`.
- Вклад принимается, только если совпадают единица, горизонт и `scenario_id`. Иначе он
  исключается с причиной `incompatible:*`.
- Позиции со статусом `needs_review` входят в срез только по утверждённому правилу
  включения (`admitted:<rule>`), с раскрытием.

Новый плагин может вносить вклад в существующий срез (`market.pnl` объявлен плагином
`market`) или объявить свой.

### 3.6. Редактор портфеля и импорт

`InstrumentTypeSpec.editor` — группы полей формы. `target` задаёт, куда пойдёт значение:
`terms`, `position` или `snapshot:<kind>`. Виды полей: `number`, `text`, `date`, `dates`,
`enum`, `boolean`, `table` (с `columns`, например ковенанты). Интерфейс строит форму сам.
`from_draft(row, ctx)` превращает введённую строку в `terms`, `params` и элементы снимка.
Каждое число становится допущением аналитика с автором и датой:
`ctx.evidence(position_id, field, value)`. Пример: `plugins/equity/editor.py`.

Без `from_draft` тип нельзя ввести в редакторе. Его позиции по-прежнему принимаются через
`POST /v1/portfolios` (бандл) и `ops/load_portfolio.py`.

### 3.7. Отчёт, правила, флаги

- `tree(result, context)` возвращает ключевое представление `details`, которое цитирует
  отчёт: ковенанты по id, вклады по каналу, производные величины. Пути имеют вид
  `/positions/<id>/<ключ>/...`. Метрики попадают в дерево сами:
  `/positions/<id>/metrics/<metric>/p50`.
- `ReportSection.render(ctx)` пишет строки через `ReportContext`. **Числа только через
  `ctx.cite(path)` или `ctx.interval(path, unit)`**: они записывают ссылку `NumberRef`, и
  валидатор V9 сверяет каждое число текста с деревом метрик. Число, написанное в обход,
  отчёт не пропустит.
- `observations` — функции `result -> (value, metric_path) | None`. `rules` сравнивают
  наблюдение с порогом и назначают `actions`. Пороги в силе — данные журнала
  (`rule_thresholds`); без утверждённого значения действует порог из объявления, и отчёт
  это раскрывает.
- `flags` — русские слова флагов. Ключ `name:` покрывает префикс, `{}` подставляет
  аргумент. Ключ `name:>` означает, что флаг несёт вложенный флаг.
- `sources` и `authors` — слова для `source_id` и `author` доказательств, на которые
  ссылаются данные плагина (например, его демо-данные), без цифр (V9). Отчёт и экраны
  показывают их вместо идентификатора. Два плагина могут назвать один источник только
  одинаково, иначе реестр не стартует.

### 3.8. Демо-кейс и снимок данных

`demo()` возвращает `DemoCase(name, bundle, snapshot, scenario, graph, completes)` —
самодостаточный кейс, который `check` считает через диспетчер платформы. `completes`
перечисляет позиции, которые обязаны рассчитаться.

Чтобы плагин участвовал в демо-стенде, его данные лежат в его папке, а общие файлы
`demo/` не правятся:

- `demo_data/portfolios/<portfolio_id>.json` — `{"parties", "instruments", "positions"}`
  плагина в демо-портфеле (так `equity` добавляет `SHARE-OIL` и `SHARE-US-TECH` в MULTI-ASSET);
- `demo_data/snapshots/<snapshot_id>.json` — `{"items"}`: их данные в демо-снимке.

`demo/catalog.py` собирает портфель из заголовка `demo/portfolios/<id>.json` и частей всех
плагинов в порядке реестра; снимок — из заголовка и элементов, упорядоченных по `item_id`.
Один эмитент может прийти от двух плагинов, если записи совпадают; разные записи с одним
идентификатором — ошибка. Часть с заголовком (`"portfolio"`) добавляет собственный
демо-портфель плагина. Каталог читают `demo/seed_demo.py`, эталонный тест кредита и тесты
платформы.

### 3.9. Чек-лист типа инструмента

- [ ] `terms`/`params`/`details` — схемы с единицами из `contracts.units`, числа с источником.
- [ ] `requirements` запрашивает данные снимка и факторы; валютный инструмент — курс и FX-фактор.
- [ ] `validate` возвращает размер позиции по каждому срезу даже для позиции, которая не считается.
- [ ] Нет молчаливых нулей и умолчаний; допущения — флагами.
- [ ] `calculate` читает только `prepared` и `context.scenario`; реализации потерь — во вклад в срез.
- [ ] Флаги, правила и разделы отчёта объявлены; числа отчёта — только через `ctx.cite`.
- [ ] Демо-кейс, `msa-plugin check` зелёный, `msa-plugin demo-run` показывает разумные P5/P50/P95.
- [ ] Приёмочные тесты в `src/msa/plugins/<plugin>/tests/` (как `plugins/equity/tests/test_equity_acceptance.py`).
- [ ] Импорты только из `msa.plugin_sdk`, `msa.contracts`, своего пакета и `market`: `lint-imports` зелёный.

## 4. Расширение графа агентов

### 4.1. Процесс как данные

Процесс (`WorkflowSpec`) объявлен данными: узлы (`NodeSpec`), рёбра, маршруты (`Route`),
этапы для экрана (`StageSpec`) и **точки расширения** (`ExtensionPoint`). Компилятор
(`graph/compiler.py`) собирает из этого граф LangGraph и вставляет агентов плагинов после
их точки.

В платформе два процесса (встроенное объявление `core`, `msa/workflows`):

- `stress_test`. Точки расширения: `after_event_parsed`, `before_scenario_approval`,
  `after_calculation`, `before_report`. Схема — в `src/msa/workflows/stress_test.py`.
- `explain_results`. Точка расширения: `after_explanation`.

Точка гарантирует набор ключей состояния (`available`). Агент может читать только их.
Никакая точка не лежит на пути в обход человеческой остановки: подтверждение сценария и
решение по отчёту обойти нельзя.

### 4.2. Агент-плагин

```python
AgentPlugin(
    agent_id="research.concentration",      # в пространстве плагина
    version="1.0.0",
    label="Концентрация хвостового риска",
    build=build,                              # (AgentContext) -> узел
    extends={"stress_test": "after_calculation"},
    consumes=("portfolio_result", "position_names"),   # только из available точки
    produces=("notes",),                      # ключи в extensions["research.concentration"]
    output_schema=ConcentrationOutput,        # pydantic; проверяется
    timeout_s=30.0, retries=1, max_iterations=4,
    before=(), after=(),                      # порядок внутри точки
    enabled_by_default=False,
)
```

- **Узел** — функция `view -> dict` или скомпилированный подграф LangGraph. У подграфа
  своё состояние и адаптеры: `subgraph_input(view) -> state` и
  `subgraph_output(state) -> dict`. Внутреннее состояние подграфа наружу не попадает.
  Циклы внутри подграфа разрешены и ограничены `max_iterations`.
- **Чтение.** Агент видит только `consumes` и идентичность прогона (`run_id`, `mode`,
  `graph_revision`, `as_of`, `portfolio_id`). Вывод другого агента читается ключом
  `ext:<agent_id>/<key>`. Такой агент должен работать раньше: `after=(...)`.
- **Запись** — только в собственное пространство `extensions[<agent_id>]` и только
  объявленные `produces`. Попытка записать ключ ядра отклоняется при компиляции.
  Недекларированный ключ отклоняется при выполнении.
- **Порядок.** Агенты одной точки раскладываются по слоям по `before`/`after`. Агенты
  одного слоя работают параллельно, следующий слой ждёт весь предыдущий.
- **Сбой** агента-плагина (исключение, таймаут, неверный вывод) записывается в его
  пространство (`{"failed": true, "errors": [...]}`) и не останавливает прогон.
- **Журнал.** Каждый узел записывается под ключом «узел/ветка + ревизия сценария» с версией
  агента и хешем входов. Повтор после остановки возвращает записанный результат. Если входы
  изменились, запись не воспроизводится молча: возникает `InputsChanged`.
- **Инструменты.** Агент объявляет MCP-инструменты в `tools` (`"<server>.<tool>"`) и
  вызывает их через `AgentContext.tools`: `call(tool, **arguments)` — вызов самого агента,
  `call_as(tool, arguments, initiator="llm", call_id=...)` — вызов, выбранный LLM,
  `functions()` — объявленные инструменты как функции для `complete_with_tools`. Шлюз
  пропускает только объявленные инструменты; вызов идёт через `ToolGateway.call_as` и
  попадает в `audit_log` с узлом агента, попыткой, инициатором (`workflow` или `llm`),
  `call_id` и хешами аргументов и ответа. Вне прогона с MCP-серверами (граф в тесте) вызов
  завершается ошибкой с причиной, и сбой остаётся в пространстве агента.
- **LLM.** `AgentContext.llm` — клиент LLM прогона; `None`, если развёртывание работает без
  модели (`mock`). Агент без модели либо работает детерминированно, либо сообщает причину.

Компилятор проверяет объявления до запуска и сообщает обо всех проблемах сразу:
неизвестные агенты и точки, отсутствующие и циклические зависимости, чтение ключа, которого
никто не даёт, запись в ядро, ограничения `retries`/`timeout`, инструменты `server.tool`,
которых нет ни у одного сервера.

### 4.3. Включение агента

- В запросе прогона: `POST /v1/demo/runs` с `"agents": ["research.concentration", ...]`.
  В интерфейсе это блок «Дополнительные агенты» на странице запуска.
- Для процесса целиком: переменная `MSA_AGENT_PLUGINS=research.concentration,research.brief`.
- `enabled_by_default=True` включает агента всегда. Этот режим — для агентов, без которых
  процесс неполон.

Выводы агентов показываются на вкладке «Портфель» в блоке «Дополнительные агенты»: видом
UI-плагина (`UiPlugin.agents`, раздел 5) или, без него, списком строк и JSON. Агенты
появляются и на шкале этапов своего процесса (`/v1/workflows`).

Пример полного агента-плагина — `plugins/research`. `research.concentration` — подграф с
циклом по срезам и адаптерами. `research.brief` читает его вывод через
`ext:research.concentration/notes`. `research.digest` вызывает собственный инструмент
плагина `research.notes.slice_digest` через `AgentContext.tools`. UI-плагин
`ui/web/src/plugins/research` рисует их выводы. Тесты `tests/graph/test_agent_plugins.py`,
`tests/graph/test_agent_tools.py` и `tests/api/test_research_digest.py` показывают: агенты
выключены по умолчанию, пишут только в своё пространство, не меняют результаты и отчёт, не
обходят решение риск-менеджера, а вызов инструмента попадает в аудит под узлом агента.

### 4.4. Агент с LLM и инструментами

Образец — объяснение результатов (`agents/explain.py`, процесс `explain_results`):

- подграф `ask → act → check` с ограничением: не больше 6 шагов модели и 12 вызовов
  инструментов;
- инструменты `mcp-runs` модель видит **без** `run_id`. Агент подставляет свой прогон, а
  сервер сверяет его с контекстом аудита, поэтому модель не может прочитать чужой прогон;
- каждое число ответа ищется в ответах инструментов: как есть, с округлением, ×100 для
  долей в процентах. Непроверенные числа получают одну попытку исправления, затем ответ
  собирается из сводки прогона без модели;
- если провайдер не вызывает инструменты (заглушка `mock` или `MSA_LLM_TOOL_CALLING=0`), тоже
  используется структурированный ответ, и причина раскрывается.

Для своего LLM-агента в плагине:

- **Клиент** — `AgentContext.llm`: `complete(messages, schema, seed)` для структурированного
  ответа, `complete_with_tools(messages, context.tools.functions(), seed)` для цикла с
  инструментами.
- **Промпт** — файл `prompts/<name>-v<N>.txt` в папке плагина, версия в силе —
  `Plugin.prompts={"<name>": "v<N>"}`. Текст читает
  `msa.plugin_sdk.prompts.prompt("<plugin_id>.<name>")`, версию —
  `current_version(...)`. Объявленный промпт без файла реестр не пропустит.
- **Инструменты** — свой MCP-сервер в `Plugin.mcp_servers`:

```python
from msa.plugin_sdk import CallContext, McpServerSpec

def register(tool, services):
    @tool
    def slice_digest(slices: list[dict], audit: CallContext) -> list[dict]:
        """Описание инструмента: его видит LLM."""
        ...

SERVER = McpServerSpec("research.notes", register, label="Заметки исследования")
```

  Имя сервера начинается с `<plugin_id>.`, в шлюзе и аудите он — `mcp-<имя>`. Декоратор
  `tool` платформа передаёт сама: он оборачивает функцию аудитом и помечает её только для
  чтения, другого способа добавить инструмент нет. У инструмента последний параметр
  `audit: CallContext`, ответ — JSON. `register` не использует `services` при объявлении:
  реестр перечисляет инструменты, вызывая `register` без них. `services`
  (`McpServices`) — контур данных (`scope`), от чьего имени вызов (`actor`) и сессия БД
  только для чтения. Инструмент проверяет границы сам: как `mcp-runs` сверяет `run_id` с
  контекстом аудита, чтобы LLM не прочитала чужой прогон.

### 4.5. Новый процесс

Новый процесс — это `WorkflowSpec` в `workflows` плагина. Состояние процесса —
`TypedDict`: ключи ядра плюс `trace` (накопление) и `extensions` (редьюсер
`merge_extensions`). Основные узлы — агенты с `core=True` из того же плагина. Узел с
`branch="<ключ>"` выполняется для каждой ветки (`Send`) и журналируется как
`<узел>/<значение>`. Человеческие остановки — узлы с `human=True`, построенные на
`interrupt` LangGraph. Нужен чекпоинтер, который переживает перезапуск; см.
`graph/checkpoint.py`. Процесс сразу появляется в `/v1/workflows`, а его этапы — на
шкале интерфейса.

### 4.6. Чек-лист агента

- [ ] Агент подключён к существующей точке; `consumes` ⊆ `available` точки (+ `ext:` предшественников).
- [ ] `produces` и `output_schema` объявлены; ключей ядра нет.
- [ ] Ограничения `timeout_s`, `retries` (1–3), `max_iterations` осмысленны.
- [ ] Инструменты — только чтение, в границах прогона, объявлены в `tools`; свой сервер — в `mcp_servers`.
- [ ] Промпты — в `prompts/` плагина с версией в `Plugin.prompts`.
- [ ] Выключен по умолчанию, пока не доказана необходимость.
- [ ] `msa-plugin check` зелёный: все процессы компилируются с агентом.
- [ ] Тест в `src/msa/plugins/<plugin>/tests/`: прогон с агентом доходит до решения риск-менеджера, результаты и отчёт не меняются.
- [ ] Вывод агента на экране: вид в `ui/web/src/plugins/<plugin>/` (`UiPlugin.agents`) или общий вид.

## 5. UI-плагин: собственный экран результата

Без UI-плагина результат нового типа показывает **стандартный вид**. Он строится из блоков
`ResultView.blocks`: `metrics` (P50 и P5 … P95 с происхождением), `table` (по JSON Pointer
в `details` и `columns`), `histogram` (`{edges, counts}`; первая метрика из `metric_ids`
отмечает на нём P5, медиану и P95), `series`, `sources`. Подписи
ключей `details`, ключей дерева отчёта (`tree`) и полей, которые называют локаторы данных,
берутся из `ResultView.labels`; ключ с подписью `""` только группирует другие и в описании
пути не показывается. Вывод агента без UI-плагина показывается
списком строк и JSON. Этого достаточно для нового плагина.

**Таблица позиций и панель разбора.** На вкладке «Позиции» одна таблица на один
`ResultView`: позиции разных типов с одним видом сравниваются на общей шкале столбца. Столбцы
— все `summary_metrics` вида, которые есть у позиций таблицы, в объявленном порядке; первая
задаёт порядок строк (сначала худшие по `MetricSpec.direction`). Разным по смыслу типам
плагин объявляет разные виды: у облигаций кредитного плагина первым идёт изменение
стоимости. Панель разбора одинакова для всех типов: статус с причиной — флаги из
`CalculationModel.review_flags`; «Важно для чтения» — флаги, которых нет ни там, ни в
`Plugin.informational_flags`; ключевые показатели — `summary_metrics` на шкале списка; затем
вид плагина; внизу свёрнутые упрощения метода — `informational_flags`. Оба списка флагов
отдаёт каталог (`review_flags`, `informational_flags`); код с `:` на конце покрывает префикс.
Поэтому вид плагина не повторяет `summary_metrics` (`MetricsBlock exclude`).

Собственные экраны — папка `ui/web/src/plugins/<plugin_id>/`:

```
plugin.json   { "plugin_id": "research", "versions": ">=1.1.0 <2.0.0",
                "components": [], "agents": ["research.concentration", "research.digest"] }
index.tsx     export default { ...meta, views: {...}, agents: {...},
                               notes?, glosses?, glossary?, baseline? }   // UiPlugin из src/plugins/sdk.ts
```

- `views` — компоненты видов результата по `ResultView.component`. Компонент получает
  `PositionViewProps`: результат, позицию, `ResultView`, артефакты прогона и `entries` —
  происхождение чисел отчёта. Готовые блоки лежат в `components/ResultBlocks.tsx`; вклады
  каналов и факторов рисует `ContributionsBlock`: сторону ухудшения он берёт из направления
  метрики, нулевые вклады называет одной строкой.
- `agents` — виды выводов агентов плагина по `agent_id`; компонент получает
  `AgentViewProps` (`output` — пространство агента, `artifacts`). Отказавший агент
  показывается общим видом с пометкой.
- `notes` — заметка, которая показывается у денежных цифр на вкладках «Портфель»,
  «Отчёт» и «Источники данных» (так кредитный плагин раскрывает калибровку PD одной строкой).
- `baseline(result, metricId)` — уровень до события величины, изменение которой меряет
  метрика (ожидаемые потери до события для их роста), или `null`. С ним таблица позиций и
  срез показывают «до → после» на шкале от нуля, изменение доли — в п.п.; без него — само
  изменение.
- `glosses(context)` — пары «идентификатор → слова» для идентификаторов плагина в тексте
  отчёта; отчёт показывает слова рядом с идентификатором, а не вместо него (так кредитный
  плагин поясняет ковенанты).
- `glossary` — термины экранов плагина с пояснением в одно предложение; `<Term name="…">`
  читает термины платформы и плагинов.
- Плагин находится автоматически (`import.meta.glob`). Роуты, вкладки и таблицы ядра
  не меняются.
- Правила интерфейса (`.impeccable.md`): P5/P50/P95 всегда вместе; число без
  происхождения не показывается; красный МТС — только айдентика и утверждение; состояние и
  тяжесть несут слово или знак, а не только цвет. Подписи берутся из каталога
  (`api/catalog.ts`), не пишутся в коде.

**Проверка совместимости при сборке.** `ui/web/src/plugins/manifest.json` генерируется из
реестра перед каждой сборкой (`npm run build` запускает `prebuild`:
`uv run --frozen msa-plugin ui-manifest`) и в git не хранится: установленные плагины, их
версии, объявленные компоненты видов и агенты. Затем `scripts/check-plugins.mjs`
сверяет с ним `plugin.json` каждого UI-плагина. Сборка падает, если UI-плагин рисует
неустановленный плагин, не понимает его версию, реализует компонент или рисует агента,
которого плагин не объявил. Компонент или агент без UI-плагина разрешён: его рисует
стандартный вид. `ops/web_build.py` пересобирает интерфейс, если установленные плагины
разошлись с манифестом прошлой сборки.

## 6. Версии и совместимость

- `Plugin.sdk` — диапазон версий SDK (`">=1.0,<2.0"`). Несовместимый плагин блокирует
  старт с названием плагина. Версия SDK — `msa.plugin_sdk.version.SDK_VERSION`, сейчас
  1.1.0: к 1.0 добавлены `calc`, `report`, `prompts`, `mcp`, `Plugin.mcp_servers`,
  `Plugin.prompts`, `Plugin.sources`, `Plugin.authors`, `AgentContext.llm` и
  `AgentContext.tools`. Плагину, который ими пользуется, нужен диапазон `">=1.1,<2.0"`.
- `Plugin.version` и `CalculationModel.version` — `x.y.z`. Прогон фиксирует версии всех
  плагинов при старте (`run.plugins`) и модель каждой позиции (`run.models`). На
  изменившемся коде прогон не продолжается: после смены версий он останавливается со
  статусом «ошибка» и причиной «код плагинов изменился после запуска».
- `scenario_id` зависит от версий факторов. Результат с другой версией фактора не
  смешивается в срезе с остальными.
- Меняете смысл метрики — меняйте её id или версию модели. Меняете схему — меняйте
  `schema_version`.

## 7. Проверка и приёмка плагина

`msa-plugin check` (`plugin_sdk/testing.py`) проверяет:

- объявления: JSON Schema схем, известные цели и единицы полей редактора, у модели есть
  обязательные метрики;
- демо-кейс: бандл проходит проверку портфеля; позиции из `completes` рассчитываются;
  обязательные метрики есть в объявленных единицах; источники чисел и данных названы;
  реализации нужной длины;
- детерминизм: одинаковые входы и seed дают одинаковый результат;
- независимость от порядка: перестановка позиций ничего не меняет;
- агрегацию: срезы собираются;
- для агентов: все процессы компилируются с включёнными агентами плагина, а объявленные
  инструменты есть у MCP-серверов;
- реестр: MCP-серверы (имя с префиксом плагина, у каждого инструмента параметр `audit`),
  промпты (файл объявленной версии), слова источников (одинаковые у всех плагинов).

Тест `tests/plugins/test_conformance.py` прогоняет проверку для каждого установленного
плагина. Свои тесты плагин держит в `src/msa/plugins/<plugin>/tests/` (пакет с
`__init__.py`); `pytest` собирает их вместе с тестами платформы, в wheel они не входят.
Приёмочные тесты пишите по образцу `plugins/equity/tests/test_equity_acceptance.py`:
нулевой шок, масштаб по количеству, валютный шок, одинаковые реализации одной бумаги,
будущие данные, пропущенные данные, несовместимая калибровка, агрегация до квантилей.

Помощники для тестов плагина — в `msa.plugin_sdk.testing`, без модулей ядра:
`check_plugin(plugin)` — проверка соответствия, `calculate_case(case)` — расчёт демо-кейса
(или его варианта с другим сценарием) через диспетчер, `tools_of(server)` — функции
MCP-сервера плагина для проверки без шлюза, `workflow_problems(plugin)` — компиляция
процессов с агентами плагина, `graph_reaching(okved, factor_id)` — минимальный граф события.
Тесты плагина могут пользоваться и ядром как стендом (`lint-imports` это разрешает только
для `msa.plugins.<id>.tests`).

## 8. Границы и совместная работа

Над системой параллельно работают несколько человек или агентов: у каждого плагина своя
папка, а ядро меняется отдельно. Граница проверяется автоматически.

**Что такое ядро.** Всё в `src/msa/` вне `src/msa/plugins/<id>/` и всё в `ui/web/src/` вне
`ui/web/src/plugins/<id>/`: SDK (`plugin_sdk`), контракты, движок, реестр, процессы и их
основные агенты (`msa/workflows`, встроенное объявление `core`), MCP ядра, API, отчёт,
экраны. Плагин — папка `src/msa/plugins/<id>/` и, по желанию, `ui/web/src/plugins/<id>/`.

**Раскладка папки плагина.**

```
src/msa/plugins/<id>/
  __init__.py        plugin = Plugin(...)
  *.py               модели, схемы, отчёт, агенты, MCP-серверы
  prompts/           промпты агентов: <name>-v<N>.txt
  demo_data/         части демо-портфелей и демо-снимка
  tests/             тесты плагина (пакет)
  README.md          что даёт плагин, его ограничения и открытые вопросы
ui/web/src/plugins/<id>/
  plugin.json        версии сервера, компоненты видов, агенты
  index.tsx          UiPlugin: views, agents, notes, glosses, glossary
```

**Правила импорта** (`uv run --frozen lint-imports`, контракты в `pyproject.toml`):

1. ядро не импортирует `msa.plugins`;
2. плагин импортирует только `msa.plugin_sdk`, `msa.contracts` и собственный пакет (тестам
   плагина разрешено ядро);
3. плагины не импортируют друг друга; исключение — базовый плагин `market`.

Контракты заданы шаблонами (`msa.plugins.*`), поэтому новый плагин не требует правки
конфигурации.

**Ядро не называет плагины.** `tests/platform/test_core_boundary.py` берёт из реестра
идентификаторы плагинов (id, типы инструментов, виды снимка, префиксы `<id>.`) и ищет их
строковыми литералами в коде ядра: Python — без docstring, TS/TSX — вне
`ui/web/src/plugins/<id>/`. Находка значит: код нужно перенести в плагин или добавить в SDK
точку расширения.

**Изменение SDK — отдельный запрос к ядру.** Если плагину не хватает возможности ядра
(функции движка, точки расширения, поля объявления), её добавляют в SDK отдельным
изменением ядра: функция остаётся в ядре, SDK её отдаёт (`plugin_sdk/calc.py`,
`plugin_sdk/report.py`), версия SDK растёт (минорная — только добавления). Плагин не
импортирует ядро в обход SDK и не правит ядро в своём изменении.

**Владельцы.** `.github/CODEOWNERS` делит репозиторий на разделы: ядро, каждый плагин (обе
его папки), `demo/`, `docs/`. Новый плагин работает и без строки в CODEOWNERS; владельцев
добавляют, когда назван состав его команды.

**Проверки перед изменением:**

```powershell
uv run --frozen pytest                  # тесты платформы и плагинов, эталон кредита
uv run --frozen ruff check .
uv run --frozen lint-imports            # правила импорта
uv run msa-plugin check                 # соответствие всех плагинов
cd ui/web; npm run build                # манифест, совместимость UI-плагинов, типы, сборка
```

Критерий границы: новый плагин (тип актива, агент с MCP-инструментом, экран) создаётся
без единой правки вне двух его папок — `msa-plugin new asset` и `msa-plugin new agent`
создают именно такой плагин, и после них все проверки выше зелёные.
