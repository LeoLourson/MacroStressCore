## Вывод

Расширение новым семейством кредитных активов организовано хорошо: объявление
`AssetModel` действительно управляет каталогом, вводом финансовых полей, проверкой
профиля, расчётом и отображением рядов. Однако обещание «один класс + регистрация,
больше ничего» справедливо только внутри существующих контрактов и методологии.
Калибровка, новые правила рекомендаций, подписи отчёта, новые драйверы и схемы
денежных потерь требуют отдельной работы.

MCP работают. Их вызывают детерминированные агенты Exposure и Quant. LLM-агенты
Causal и Advisory не имеют доступа к инструментам: клиент реализует только
структурированный ответ, без tool-calling. Изменением промпта это не исправить.

## Что уже расширяется автоматически

1. `assets/base.py:120`: модель объявляет типы, поля, единицы, границы, допущения,
   полноту раскрытия, ряды, ковенанты, решающие метрики, PD-сегмент и review-флаги.
2. `assets/__init__.py:18`: регистрация и поиск модели по строковому типу.
   `contracts/asset.py:57` проверяет тип через этот реестр.
3. `engine/model.py:85`: автоматически появляется `track_a_v3/<asset_type>`.
   `engine/pipeline.py:249` выбирает модель через `model_for()`.
4. `agents/exposure.py:67`: обязательные поля и полнота берутся из модели.
5. `api/routers/asset_types.py`: каталог передаётся редактору. `ui/web/src/api/catalog.ts`
   и `lib/portfolioFields.ts` строят поля и подписи из него.
6. `db/models.py:65`: `asset_type` хранится строкой без перечисления разрешённых типов;
   финансовые параметры хранятся JSON. Новый тип в существующем контракте не требует
   миграции БД.
7. Тест факторинга проверяет каталог, V2, `run_asset`, Quant, квантили и денежные потери.
   Его Quant использует прямой вызов модели, без MCP; это ограничение исходного теста.
   В рамках аудита отдельно проверен факторинг через настоящий FastMCP Client.

Здесь и далее Python-пути без префикса относятся к `src/msa/`.

## Находки

### A1 — P1: отсутствующие признаки PD молча исключаются из скоринга

`engine/credit.py:176–181` проверяет лишние признаки, но не отсутствующие признаки
калибровки. Суммирование идёт по переданным `features`, результат сохраняет
`calibrated=True`.

Воспроизведено: корпоративная калибровка содержит `r_icr`, `r_lev`,
`ebitda_nonpositive`; передан только `r_icr`. Результат совпадает с явной подстановкой
нулей в два остальных признака и остаётся откалиброванным. Именно подмножество
признаков использует демонстрационный Factoring.

Следствие: успешный технический тест нового типа не доказывает применимость PD.
Нужен явный контракт признаков сегмента: обязательные признаки, разрешённые
необязательные признаки с объявленными значениями, отказ на неполноту. Для нового
семейства следует выбирать подходящую калибровку, а не автоматически наследовать
корпоративную.

### A2 — P1: дата расчёта не ограничивает все финансовые данные

`api/run_service.py:63` загружает портфель раньше определения `as_of`.
`api/agent_service.py:87` не передаёт дату в загрузку портфеля. В рабочем контуре
`AssetsRepository.get_asset()` берёт последнюю отчётность без ограничения даты,
если `as_of` не передан.

Позже MCP `get_statement` читает отчётность с правильным `as_of`, но
`agents/exposure.py:53` использует её дату/стандарт для DQ и не переносит
`statement['parameters']` в финансовые данные профиля. `get_peers` также не принимает
дату, в отличие от `find_peers`.

Локально воспроизведено: профиль содержит 5000, переданная историческая отчётность —
2500, после `build_profile` остаётся 5000. Цепочка загрузки рабочего портфеля
проверена по коду; полный исторический прогон рабочей БД не выполнялся.

Следствие: исторический стресс может использовать более поздние числа, хотя MCP
успешно вернул историческую отчётность. Определять дату до загрузки портфеля,
передавать её во все чтения и явно установить источник финансовых значений.

### A3 — P2: единица любого ковенанта в редакторе — ratio

`api/portfolio_draft.py:107` записывает `unit='ratio'`, хотя `Series.unit` может
быть денежной величиной, днями и т. д. `CovenantMetric` своей единицы не имеет.

Воспроизведено: новый ковенант на `income`, объявленный в `RUB_million`, сохранён
в профиле с единицей `ratio`. Проверка V2 касается финансовых полей и этого не ловит.
Единицу следует выводить из объявления соответствующего ряда и проверять на входе.

### A4 — P2: объявленные границы fraction игнорируются

`assets/base.py:166–167` заменяет `minimum`/`maximum` для `fraction` на 0 и 1.
Воспроизведено: поле с диапазоном 0.10–0.20 принимает 0.90 без замечаний.
Нужно пересекать объявленный диапазон с базовым диапазоном единицы.

### A5 — P2: неполная реализация плагина может дать неполный результат без причины

`assets/__init__.py:18` проверяет занятость типа и наличие объявленных рядов для
метрик, но не фактический результат `evaluate()`. `engine/pipeline.py:703–706`
молча пропускает отсутствующую решающую метрику. `_trajectory()` назначает
необъявленному ряду `fraction/probability` — это полезно для системного `risk_score`,
но одновременно маскирует другие необъявленные выходы.

Воспроизведено: плагин объявляет `icr`, но возвращает пустые `metrics`.
Расчёт завершается, `icr` отсутствует в квантилях; единственный флаг —
`calibration_synthetic`, специальной причины неполноты нет.

Нужна проверка объявления при регистрации и выходов после `evaluate`: уникальные
имена, известные единицы/виды рядов, непустое корректное `disclosure`, наличие
обязательных метрик и согласованные формы массивов. Неопределённые отношения
должны обрабатываться по явной политике, без запрета всех NaN подряд.

### A6 — P2: рекомендации и текст отчёта расширяются не полностью

`reporting/recommendations.py:29` знает фиксированный набор наблюдений:
`icr_p50`, вероятность ковенанта, изменение PD/score, потерь, вклад ставки/FX.
Произвольная `decision_metric`, например DSCR, автоматически не становится
наблюдением правила. `apply()` требует ровно R1–R5.

`reporting/wording.py:26` хранит собственные названия ковенантов;
подписи новых флагов добавляются также в `ui/web/src/lib/labels.ts`.
UI-каталог динамический, но словари рядов/метрик глобальны по имени, поэтому
одинаковые имена с разным смыслом у разных типов конфликтуют.

Это ограничения расширения, а не доказательство неправильных результатов текущих
пяти типов. Для полноценного расширения нужны общие метаданные подписей и
явное сопоставление новых метрик с правилами рекомендаций.

## Где заканчивается расширение одним классом

| Новый тип | Оценка интеграции |
|---|---|
| Ещё один вариант существующего корпоративного кредита | Низкая сложность: модель/поля, регистрация, данные и проверки |
| Факторинг с собственной экономикой и признаками PD | Средняя: дополнительно калибровка, ковенанты, рекомендации, граничные случаи |
| Актив с меняющимися EAD/LGD, амортизацией, выборкой лимита | Нужен новый контракт денежных потерь: сейчас `_Asset.expected_loss()` заполняет весь горизонт постоянными `profile.ead` и `profile.lgd` |
| Акции, опционы, валютные позиции | Высокая: контракт профиля кредитный, RUB-only, семь фиксированных драйверов, кредитный target/агрегация; `market()` сам по себе этого не решает |

`InputField` поддерживает числовые скаляры. Графики платежей, категории, даты и
структурированные параметры не являются произвольными полями плагина.
Новые единицы требуют согласования `contracts/common.py:Unit` и UI `FieldUnit`.
Новые драйверы затрагивают контракты графа/сценария, передачу шока, промпты и UI.
Даже в движке сохраняется специализированный `bond_market` в реестре.

Практический набор работ для нового типа: формула и области применимости;
объявление и регистрация; PD-калибровка/правила риска; демонстрационный профиль;
тесты нулевого и стрессового сценария, пропусков, ковенантов, агрегации и отчёта;
сквозной прогон через API/MCP и проверка редактора.

## Текущее устройство MCP

`AgentService → ToolGateway → FastMCP Client (in-memory transport) → tool → DB/engine`.
Это настоящий обмен MCP внутри процесса API, без отдельного сетевого сервера.
Gateway использует выделенный event loop. Вызовы обёрнуты аудитом;
для чтения БД применяются контур и read-only сессии.

| Сервер / инструмент | Кто выбирает вызов |
|---|---|
| `mcp-portfolio.get_statement` | Exposure для выбранного актива |
| `mcp-portfolio.get_peers` | Exposure при DQ < 0.4 |
| `mcp-portfolio.find_peers` | Exposure, если заданная группа аналогов пуста |
| `mcp-models.run_model` | Quant после проверок профиля и сценария |

Отсутствуют MCP-инструменты `list_models`/`describe_model`: одноимённые функции
есть в Python-каталоге, но сервер регистрирует только `run_model`.
Документы, поиск источников, рыночные данные и stdio-запуск были удалены при переносе,
что зафиксировано в `docs/audit.md`.

`McpAssets` связывает автоматические вызовы с портфелем; сам сервер принимает
`portfolio_id` аргументом. Поэтому будущий LLM-адаптер должен задавать контур,
портфель, дату и audit-контекст сервером, а не доверять этим аргументам модели.

### Почему LLM не вызывают инструменты

- `agents/__init__.py:50`: `tools` получает Quant; Causal и Advisory получают `llm`.
- `integrations/llm/client.py:70`: HTTP payload содержит `messages` и
  `response_format`, но не `tools`/`tool_choice`.
- `_content()` читает только `message.content`; `tool_calls` не разбираются.
- Нет цикла «выбор инструмента → исполнение → role=tool → следующий ответ».
- Causal строит JSON по документу и ОКВЭД. Advisory редактирует уже рассчитанный
  текст; его действия определены таблицей правил, а числа проверяет V9.

Это архитектурное ограничение приложения. Настройки MCP редактора и добавление
текста в `CLAUDE.md` не подключают инструменты к этой LLM.

## Функции, ради которых стоит добавить LLM-вызовы

Ниже предложения, они ещё не реализованы.

1. **Объяснение результата по запросу аналитика.** «Почему актив исключён?» / «Что
   даёт рост потерь?» Инструменты `get_run_summary`, `get_asset_result`, `get_metric_trace`.
   Возвращать компактные метрики с источниками и путями, проверять числа ответа.
   Использовать существующие результаты и trace, а не повторять расчёт.
2. **Обоснование каузальных связей.** Causal запрашивает фрагмент документа,
   описание деятельности или утверждённую отраслевую методику, когда исходного
   текста недостаточно. Потребуются инструменты чтения/поиска и расширение
   проверки evidence: сейчас ссылки проверяются относительно одного документа.
   Результат остаётся проектом графа для подтверждения аналитиком.
3. **Сравнение вариантов сценария.** По явному запросу пользователя LLM формирует
   вариант, валидатор проверяет допустимые изменения, расчёт сравнивает его с
   утверждённой базой. Инструменты `describe_model`, `validate_scenario`,
   `compare_scenarios`. Вариант не заменяет утверждённый прогон.
4. **Объяснение пробелов данных и подбор аналогов.** Показать отсутствующие поля,
   подходящих аналогов и основания выбора. Подстановки проходят методические
   проверки и подтверждение; текущего среднего абсолютных показателей компаний
   одной отрасли недостаточно для такого решения.

Для обязательного расчёта каждого выбранного актива нынешний детерминированный
Quant удобнее: нет задачи, требующей выбора инструмента моделью. Полезный критерий
агентности — дополнительный обоснованный ответ или найденное свидетельство,
а не количество MCP-вызовов.

### Минимальная реализация LLM-инструментов

- Отдельный метод клиента с tool-calling, сохранив `complete()` для JSON-ответов.
- MCP-схемы → функции провайдера; обработка `tool_calls`, результатов и ошибок,
  ограниченное число итераций и явные таймауты.
- Разные наборы инструментов для объяснения, Causal и сценарных экспериментов.
- Сервер задаёт права, portfolio/run/as_of/audit-контекст. Действующий запрет
  внешней LLM для рабочего контура сохраняется.
- Результаты инструментов компактны: `run_model` сейчас возвращает в том числе
  массивы реализаций, которые не нужны в контексте LLM.
- Аудит различает инициатора (`workflow`/`llm`), сохраняет идентификатор вызова,
  ссылки на вход/выход и ошибку; сейчас tool-аудит содержит в основном статус,
  имя, run/node/attempt и длительность.
- Тесты вызова/отказа, ограничения области данных, повторов, лимита итераций,
  неподдерживаемого tool-calling провайдера и финального ответа с проверкой чисел.
